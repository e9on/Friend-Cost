# 친구비 측정기 — 관계 점수 계산 규칙

| 항목 | 값 |
| --- | --- |
| 버전 | v1.4 |
| 최종 수정일 | 2026-08-26 |
| 상위 문서 | `친구비-측정기-서비스-기준-명세.md` |
| 데이터 구조 | `데이터-계약-명세.md` |

## 1. 문서 목적

이 문서는 `ConversationData`와 `RelationshipAnalysisData`로부터 `RelationshipScoreData`를 만드는 **산식과 가중치**를 정의한다.

여기 정의된 모든 계산은 **일반 코드로 수행하며 LLM을 호출하지 않는다.** 같은 입력에 대해 항상 같은 결과가 나와야 한다.

필드명과 타입은 `데이터-계약-명세.md`를 따른다. 이 문서에서 필드를 새로 정의하지 않는다.

## 2. 계산 순서

산식 사이에 의존 관계가 있으므로 반드시 아래 순서로 계산한다.

```text
1. 세션 분할            (ConversationData만 사용)
2. firstContactRatio    (LLM 불필요)
3. avgReplySeconds      (LLM 불필요)
4. contactBalance       (LLM 불필요)
5. intimacy             (4 + RelationshipAnalysisData)
6. breakupRisk          (2~4 + RelationshipAnalysisData)
7. friendFee            (5, 6, 4의 파생)
8. confidence           (ConversationData.meta)
```

1~4번은 LLM 호출 없이 계산 가능하다. 기준 명세 8장의 "코드로 계산 가능한 작업은 LLM에 맡기지 않는다" 원칙이 여기에 해당한다.

## 3. 상수

| 상수 | 값 | 용도 |
| --- | ---: | --- |
| `SESSION_GAP_SECONDS` | 21600 (6시간) | 대화 세션 구분 기준 |
| `REPLY_MAX_SECONDS` | 21600 (6시간) | 답장 간격 유효 상한 |
| `REPLY_FLOOR_SECONDS` | 300 (5분) | 답장 지연 점수의 하한 기준 |
| `REPLY_CEIL_SECONDS` | 21600 (6시간) | 답장 지연 점수의 상한 기준 |
| `TRIM_RATIO` | 0.10 | 절사평균에서 잘라낼 상위 비율 |
| `FEE_BASE` | 100000 | 친구비 기준가 (원) |
| `FEE_CALIBRATION_MEAN` | 0.400 | 보정 곡선의 중심 (시뮬레이션 산출) |
| `FEE_CALIBRATION_STDDEV` | 0.099 | 보정 곡선의 폭 (시뮬레이션 산출) |
| `FEE_CURVE_STRENGTH` | 0.7 | 보정 세기. 1.0이면 순수 분위수 |
| `FEE_MIN` | 1000 | 친구비 하한 (원) |
| `FEE_MAX` | 100000 | 친구비 상한 (원) |
| `MIN_MESSAGES` | 15 | 분석 최소 메시지 수 |
| `RELIABLE_MESSAGES` | 40 | 신뢰도 `high` 기준 메시지 수 |

## 4. 세션 분할

`sentAt`이 `null`이 아닌 메시지만 사용한다. 시간순으로 훑으며 직전 메시지와의 간격이 `SESSION_GAP_SECONDS`를 초과하면 새 세션을 시작한다.

```text
session[0] 시작
for i in 1..n-1:
    if messages[i].sentAt - messages[i-1].sentAt > SESSION_GAP_SECONDS:
        새 세션 시작
```

6시간을 기준으로 삼는 이유는 수면 시간을 대화 공백이 아니라 **세션 종료**로 보기 위해서다. 이 처리를 하지 않으면 자정 전후 메시지 하나가 평균 답장 속도를 통째로 왜곡한다.

## 5. firstContactRatio (먼저 연락 비율)

각 세션의 **첫 메시지 화자**를 집계한다.

```text
firstContactRatio = (speaker == "me"인 세션 수) / (전체 세션 수)
```

세션 수가 3 미만이면 통계적 의미가 없으므로 `0.5`로 고정하고 `confidence`를 `low`로 강등한다.

## 6. avgReplySeconds (평균 답장 속도)

화자가 바뀌는 지점마다 답장 간격을 수집한다.

```text
A의 마지막 연속 메시지 시각 → B의 첫 메시지 시각 = B의 답장 간격
```

수집 규칙:

- 양쪽 메시지의 `sentAt`이 모두 `null`이 아닐 때만 수집한다.
- 간격이 `REPLY_MAX_SECONDS`를 초과하면 **버린다.** 답장이 아니라 새 세션의 시작으로 본다.
- 같은 화자가 연속으로 여러 메시지를 보낸 경우, 마지막 메시지를 기준으로 삼는다.

집계 규칙:

```text
표본을 오름차순 정렬
상위 TRIM_RATIO(10%)를 잘라낸다
남은 값의 산술평균을 정수로 반올림
```

표본이 3개 미만이면 `null`을 반환한다. `me`와 `peer`를 각각 따로 계산한다.

절사평균을 쓰는 이유는 답장 간격 분포가 한쪽으로 심하게 치우쳐 있어서, 단순 평균이 소수의 늦은 답장에 끌려가기 때문이다. 사용자에게는 "평균 답장 속도"로 표시하되 계산은 이 규칙을 따른다.

## 7. contactBalance (연락 균형도)

```text
countMe   = speaker == "me"인 메시지 수
countPeer = speaker == "peer"인 메시지 수
total     = countMe + countPeer

contactBalance = round(100 × (1 - |countMe - countPeer| / total))
```

| 메시지 비율 | contactBalance |
| --- | ---: |
| 50 : 50 | 100 |
| 60 : 40 | 80 |
| 70 : 30 | 60 |
| 90 : 10 | 20 |

## 8. intimacy (친밀도)

```text
intimacy = round(
    0.35 × (emotionalTone.me    + emotionalTone.peer)    / 2
  + 0.25 × (affectionSignals.me + affectionSignals.peer) / 2
  + 0.20 × contactBalance
  + 0.20 × topicDepth
)
```

가중치 합이 1.0이고 모든 항이 0~100이므로 결과는 자동으로 0~100에 들어간다.

감정 온도에 가장 큰 비중을 두되, 말로만 친한 관계와 실제로 주고받는 관계를 구분하기 위해 `contactBalance`를 함께 넣는다.

## 9. breakupRisk (손절 위험도)

먼저 보조 점수 두 개를 계산한다.

**답장 지연 점수** — 상대의 답장이 느릴수록 높다.

```text
r = avgReplySeconds.peer
k = 상대가 답할 차례였던 횟수 (간격 길이와 무관하게 센다)

r == null 이고 k >= MIN_REPLY_SAMPLES  → replyDelayScore = 100
r == null                              → replyDelayScore = 0
r <= REPLY_FLOOR_SECONDS               → replyDelayScore = 0
r >= REPLY_CEIL_SECONDS                → replyDelayScore = 100
그 외:
  replyDelayScore = round(
      100 × ln(r / REPLY_FLOOR_SECONDS) / ln(REPLY_CEIL_SECONDS / REPLY_FLOOR_SECONDS)
  )
```

**`r == null` 을 두 경우로 나누는 이유.** 표본이 없다는 것에는 서로 다른 두 사실이 섞여 있다.

| 상황 | 뜻 | 점수 |
| --- | --- | --- |
| 시각이 복원되지 않았거나 상대가 답할 차례 자체가 없었다 | **모른다** | 0 |
| 답할 차례는 여러 번 있었는데 6시간 안에 답한 적이 한 번도 없다 | **측정된 사실** | 100 |

앞은 데이터가 없는 것이고 뒤는 데이터가 있는 것이다. 둘을 같게 다루면 **답장이 느릴수록 위험이 낮아진다.**

2026-08-26 실측에서 이 역전이 실제로 나왔다.

| 관계 | 상대 답장 간격 | 남은 표본 | 지연 점수 |
| --- | --- | --- | ---: |
| 절친 | 0.1시간 | 0.1시간 | 0 |
| 용건 위주 | 0.2~2시간 | 1.1시간 | **61** |
| 소원해지는 중 | 2~12시간 | **없음** | **0** |
| 일방적 | 4~24시간 | **없음** | **0** |

반나절씩 답장하지 않는 상대가 "위험 없음"으로 나온다. 사용자에게 그대로 보이는 값이다.

`MIN_REPLY_SAMPLES` 를 조건에 두는 이유는 한두 번의 공백으로 단정하지 않기 위해서다. 짧은 대화에서는 여전히 0이다.

| 상대 답장 속도 | replyDelayScore |
| --- | ---: |
| 5분 이하 | 0 |
| 15분 | 26 |
| 30분 | 42 |
| 1시간 | 58 |
| 2시간 | 74 |
| 6시간 이상 | 100 |

로그 스케일을 쓰는 이유는 5분과 30분의 차이가 3시간과 4시간의 차이보다 관계적으로 크기 때문이다.

상한을 6시간으로 둔 이유는 `REPLY_MAX_SECONDS`가 6시간이어서 그보다 긴 간격은 답장이 아니라 새 세션으로 처리되기 때문이다. 상한을 24시간처럼 더 크게 잡으면 `avgReplySeconds`가 결코 도달할 수 없는 구간이 생겨 100점이 나오지 않는다.

**세 상수가 모두 6시간인 것은 우연이 아니다.** `SESSION_GAP_SECONDS`가 세션 경계를 정하고, 그 경계가 곧 답장으로 인정하는 상한(`REPLY_MAX_SECONDS`)이며, 점수 상한(`REPLY_CEIL_SECONDS`)도 같은 지점이어야 눈금이 끊기지 않는다. 다만 이 때문에 6시간을 **넘긴** 간격은 표본에서 사라지므로, 위 표의 `k` 조건이 없으면 그 구간이 통째로 0점이 된다.

**연락 불균형 점수** — 연락이 한쪽으로 기운 정도.

```text
countImbalance      = 100 - contactBalance
initiationImbalance = 200 × |firstContactRatio - 0.5|

contactImbalanceScore = round(0.5 × countImbalance + 0.5 × initiationImbalance)
```

| contactBalance | firstContactRatio | contactImbalanceScore |
| ---: | ---: | ---: |
| 100 | 0.50 | 0 |
| 100 | 1.00 | 50 |
| 0 | 0.50 | 50 |
| 74 | 0.63 | 26 |
| 0 | 1.00 | 100 |

**두 가지를 함께 보는 이유**가 있다. 서로 다른 것을 재기 때문이다.

- **연락 균형도**는 누가 더 많이 말하는가를 본다
- **먼저 연락 비율**은 누가 대화를 여는가를 본다

메시지 수는 반반인데 항상 한쪽이 먼저 말을 거는 관계가 있다. 균형도만 보면 완벽해 보이지만, **한쪽이 멈추면 대화도 멈추는 관계**다. 사용자가 가장 알고 싶어 하는 것이 바로 이 차이다.

방향은 따지지 않는다. 내가 늘 먼저 걸든 상대가 늘 먼저 걸든, 한쪽만 끌고 가는 관계는 마찬가지로 위태롭다.

**약속 불이행 점수**

```text
promiseBreakScore = round(100 × declined / max(1, proposed))
```

**금전 미해결 점수**

```text
moneyRiskScore = round(100 × max(0, lent - resolved) / max(1, lent))
```

최종 산식:

```text
breakupRisk = round(
    0.30 × conflictLevel
  + 0.15 × contactImbalanceScore
  + 0.10 × (100 - effortLevel.peer)
  + 0.20 × replyDelayScore
  + 0.15 × promiseBreakScore
  + 0.10 × moneyRiskScore
)
```

가중치 합은 1.00이다.

## 10. friendFee (친구비)

친구비는 **독립 지표가 아니라 파생 지표다.** `intimacy`, `contactBalance`, `breakupRisk`가 먼저 확정된 뒤에 계산한다.

### 10.1 원시 품질 비율

```text
qualityRatio = (intimacy / 100)
             × (0.5 + 0.5 × contactBalance / 100)
             × (1 - breakupRisk / 200)
```

각 항의 의미:

| 항 | 역할 | 범위 |
| --- | --- | --- |
| `intimacy / 100` | 관계의 기본 가치 | 0.00 ~ 1.00 |
| `0.5 + 0.5 × contactBalance / 100` | 균형 보정. 한쪽만 노력해도 절반은 인정 | 0.50 ~ 1.00 |
| `1 - breakupRisk / 200` | 위험 할인. 최대 50%까지만 깎는다 | 0.50 ~ 1.00 |

위험도 할인을 `/200`으로 둔 이유는, 관계가 아무리 나빠도 친구비가 0원이 되면 결과가 모욕적으로 읽히기 때문이다.

### 10.2 보정 곡선

원시 비율을 그대로 금액으로 바꾸지 않는다. **세 항의 곱은 값이 가운데로 몰리기 때문이다.**

그대로 쓰면 중간 50%가 33,000~46,000원에 들어온다. 사용자가 친구 셋을 재서 38,000·41,000·44,000원을 받으면, 서비스는 아무것도 알려주지 못한 것이다.

```text
percentile = Φ((qualityRatio - FEE_CALIBRATION_MEAN) / FEE_CALIBRATION_STDDEV)
position   = FEE_CURVE_STRENGTH × percentile
           + (1 - FEE_CURVE_STRENGTH) × qualityRatio

friendFee  = clamp(FEE_MIN, FEE_MAX, round_to_nearest(
                 FEE_MIN + position × (FEE_MAX - FEE_MIN), 1000))
```

`Φ` 는 정규분포의 누적분포함수다.

**왜 정규 CDF인가.** 있을 법한 관계 3,000건을 시뮬레이션한 결과 원시 비율이 정규분포에 매우 가까웠다(평균 0.400, 표준편차 0.099, 분위수 최대 오차 0.013). 정규분포를 자기 CDF에 통과시키면 균등 분포가 되므로, 친구비가 **"우리가 본 분포에서 상위 몇 %"** 라는 뜻을 갖는다.

**왜 원래 비율을 섞는가.** 순수 분위수만 쓰면 양 끝이 뭉개진다. 평균에서 2.5표준편차만 벗어나도 CDF가 0이나 1에 붙어, 서로 다른 좋은 관계가 전부 99,000원이 되고 서로 다른 나쁜 관계가 전부 1,000원이 된다. 가운데를 벌리려다 양 끝을 잃는 셈이다. 원래 비율을 30% 섞으면 양 끝에서도 순서가 유지된다.

**순서는 보존된다.** 두 항 모두 단조 증가하므로 더 나은 관계가 더 낮은 친구비를 받는 일은 없다.

계산 예시:

| intimacy | contactBalance | breakupRisk | qualityRatio | friendFee |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 100 | 0 | 1.000 | 100,000원 |
| 71 | 100 | 18 | 0.646 | 89,000원 |
| 64 | 74 | 38 | 0.451 | 63,000원 |
| 60 | 60 | 30 | 0.408 | 50,000원 |
| 25 | 40 | 65 | 0.118 | 5,000원 |
| 0 | 0 | 100 | 0.000 | 1,000원 |

### 10.3 보정값은 합성 데이터에서 나왔다

`FEE_CALIBRATION_MEAN` 과 `FEE_CALIBRATION_STDDEV` 는 **실제 사용자 데이터가 아니라 시뮬레이션**에서 얻은 값이다.

실제 모델을 붙이면 Analysis Agent의 출력 분포가 다를 수 있다. 예를 들어 모델이 감정 온도를 늘 60~80으로만 답한다면 원시 비율의 분포도 달라지고, 보정이 어긋난다.

**실측 후 `tools/calibrate_fee.py` 로 다시 구한다.** 그때 이 문서의 계산 예시 표도 함께 갱신한다.

## 11. confidence (신뢰도)

```text
기본 판정:
  messageCount >= RELIABLE_MESSAGES AND timeCoverage >= 0.6  → high
  messageCount >= RELIABLE_MESSAGES OR  timeCoverage >= 0.6  → medium
  그 외                                                       → low

보정:
  meta.sampled == true       → 한 단계 강등
  세션 수 < 3                 → low로 고정
```

강등은 `high → medium → low` 순이며 `low`에서 더 내려가지 않는다.

`messageCount`가 `MIN_MESSAGES`(15) 미만이면 점수를 계산하지 않고 `TOO_FEW_MESSAGES` 오류로 종료한다. 신뢰도를 낮춰 보여주는 것보다 분석을 거절하는 편이 낫다.

## 12. 경계 처리

| 상황 | 처리 |
| --- | --- |
| `avgReplySeconds`가 양쪽 다 `null` | `replyDelayScore = 0`, `confidence` 한 단계 강등 |
| `promiseSignals.proposed == 0` | `promiseBreakScore = 0` |
| `moneySignals.lent == 0` | `moneyRiskScore = 0` |
| `timeCoverage == 0` | 세션 분할 불가. `firstContactRatio = 0.5`, `avgReplySeconds = null`, `confidence = low` |
| 계산 결과가 범위를 벗어남 | 0~100 또는 `FEE_MIN`~`FEE_MAX`로 clamp. 예외를 던지지 않는다 |

`RelationshipAnalysisData`의 값이 정의된 범위를 벗어나 도착한 경우(LLM 출력 이상), 검증 단계에서 clamp한 뒤 계산을 진행한다. 검증 절차는 `데이터-계약-명세.md` 11장의 `LLM_SCHEMA_INVALID` 처리를 따른다.

## 13. 전체 계산 예제

`데이터-계약-명세.md`의 예시 값을 실제로 통과시킨 결과다. **구현 시 회귀 테스트 고정값으로 사용한다.**

### 입력

`ConversationData.meta`

## 14. 가중치 조정 원칙

이 문서의 가중치는 **초기값이며 실사용 데이터로 조정될 것을 전제한다.**

- 가중치는 코드에 상수로 흩어놓지 않고 설정 파일 한 곳에 모은다.
- 가중치를 바꾸면 이 문서의 계산 예시 표도 함께 갱신한다.
- 가중치 합은 항상 1.00을 유지한다. 합이 달라지면 점수 범위가 깨진다.
