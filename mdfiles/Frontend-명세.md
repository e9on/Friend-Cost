## 1. 문서 목적

이 문서는 웹 클라이언트의 **화면 구성, 상태 전이, 사용자에게 지켜야 할 약속**을 정의한다.

색이나 여백 같은 시각적 세부는 다루지 않는다. 그건 코드가 진실이다. 여기 적는 것은 **바꾸면 안 되는 것**이다.

## 2. 전제

| 항목 | 값 |
| --- | --- |
| 기반 | React + TypeScript, Vite |
| 배포 | 정적 호스팅 (기준 명세 8장) |
| 화면 기준 | **모바일 우선** |
| 인증 | 없음 |
| 저장소 | 동의 기록 한 줄만. 그 밖에는 아무것도 남기지 않는다 |

**모바일 우선인 이유**는 취향이 아니다. 대화 캡처는 휴대폰에서 찍고, 결과도 휴대폰에서 보고, 공유도 휴대폰에서 한다. 데스크톱은 폭만 제한하면 되는 부수적 경우다.

**localStorage 에는 최초 동의 여부만 남긴다.** 기준 명세 5장은 사용자의 대화와 개인정보를 남기지 말라는 것이지 모든 저장을 금지하는 것이 아니다. 남기는 값은 `true` 하나이고, 대화·결과·식별자는 여전히 남기지 않는다.

이것 없이는 **최초 입장 시 동의**를 구현할 수 없다. 새로고침할 때마다 동의를 다시 받으면 사용자는 동의를 읽지 않고 닫는 법을 배운다. 그러면 동의 절차 자체가 무의미해진다.

**저장하는 순간 「개인정보 보호법」제30조 제1항의 "자동 수집 장치의 설치·운영 및 거부에 관한 사항"이 처리방침 기재 의무가 된다.** 코드와 문서를 함께 고친다(`legal/개인정보-처리방침.md` 14장).

### 2.1 최초 입장 동의

처음 들어온 사람에게 동의를 받기 전에는 어떤 화면도 보여주지 않는다.

「개인정보 보호법」제22조는 **각 동의 사항을 구분해 각각 받으라**고 한다. 하나로 묶은 체크박스는 그 요건을 채우지 못한다.

| 항목 | 근거 |
| --- | --- |
| 만 14세 이상입니다 | 개보법 제22조의2 |
| 이용약관에 동의합니다 | 약관규제법 제3조 |
| 개인정보 수집·이용에 동의합니다 | 개보법 제15조 |
| 개인정보를 미국(Groq, Inc.)으로 이전하는 데 동의합니다 | 개보법 제28조의8 |

넷 다 필수다. **선택 동의는 두지 않는다.** 광고도 마케팅도 하지 않으므로 선택 항목이 없고, 그래서 "선택 동의를 강요했다"는 문제가 생길 여지도 없다.

편의를 위한 "모두 동의" 버튼은 두되 **개별 체크박스를 함께 보인다.** 묶음만 두면 구분해 받았다고 볼 수 없다.

개인정보 수집·이용 항목에는 **요약을 모달 안에 직접 보여준다.** 링크만 걸면 알렸다고 보기 어렵다.

```text
수집 항목  대화 캡처 이미지, 추출된 대화 텍스트, 접속 IP
목적       관계 지표 산출 및 결과 제공
보유 기간  20분 후 자동 삭제 (IP는 저장하지 않음)

동의를 거부할 수 있으나, 거부하면 서비스를 이용할 수 없습니다.
```

**마지막 줄을 빼지 않는다.** 거부권 고지는 의무다.

약관과 처리방침 **전문**은 모달로 연다. 앱 밖으로 내보내지 않는다. 휴대폰에서 돌아오지 못하는 사용자가 생기고, 문서가 두 벌이 되면 한쪽만 고쳐진다.

동의 기록은 `localStorage` 에 남기며 **키에 버전을 붙인다.** 약관이 바뀌면 다시 받아야 하는데 버전이 없으면 방법이 없다.

`localStorage` 를 쓸 수 없는 환경(사파리 프라이빗 등)에서는 접근 실패를 삼키고 **매번 동의를 받는다.** 앱이 죽는 것보다 낫다.

## 3. 화면 흐름

```text
    업로드
      │ 분석 시작
      ▼
    진행  ◄── 폴링
      │
      ├── 완료 ──▶ 결과 ──▶ (다시 하기) ──▶ 업로드
      │
      └── 실패 ──▶ 실패 ──▶ (다시 하기) ──▶ 업로드
```

| 상태 | 의미 |
| --- | --- |
| `idle` | 업로드 화면 |
| `uploading` | 이미지 전송 중 |
| `running` | 서버가 분석 중. 폴링 |
| `done` | 결과 표시 |
| `failed` | 실패 안내 |

상태는 훅 하나(`useAnalysis`)가 소유한다. 화면은 상태를 읽어 그리기만 한다.

## 4. 업로드 화면

### 4.1 사전 검증

서버가 다시 검증하지만 여기서 먼저 거른다. **헛된 왕복을 줄이기 위해서다.**

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 개수 | 1~10장 | `API-명세.md` 4장 |
| 형식 | PNG, JPG, WEBP | 같은 곳 |
| 개별 용량 | 5MB | 같은 곳 |
| 전체 용량 | 20MB | 같은 곳 |

**이 값이 서버와 어긋나면 사용자는 서버에 가서야 거절당한다.** API 명세가 바뀌면 여기도 함께 고친다.

해상도는 검사하지 않는다. 브라우저에서 재려면 이미지를 모두 디코드해야 해서 느리다. 서버가 헤더로 판별한다.

### 4.2 이미지 순서

**업로드 순서가 곧 시간 순서다.** 사용자에게 이 사실을 알린다.

- 각 미리보기에 순번을 표시한다
- "번호 순서대로 시간이 흐른다고 봅니다"를 문구로 노출한다

순서가 뒤바뀌면 시각 복원이 어긋나 결과가 통째로 틀어진다. 조용히 두면 사용자는 알 수 없다.

### 4.3 업로드 직전 확인

분석 시작 전에 확인시킨다.

> 내가 참여한 1:1 대화이고, 만 14세 이상입니다.

체크하지 않으면 시작 버튼이 잠긴다. 근거는 `운영-보안-법적고지-명세.md` 3장.

**최초 입장 동의(2.1)와 겹쳐 보이지만 시점이 다르다.** 저쪽은 서비스 이용 전체에 대한 1회 동의이고, 이쪽은 **지금 올리는 이 대화**에 대한 확인이다. 후자를 없애면 매번 자각시키는 장치가 사라진다.

**이것이 상대방의 동의를 보장하지는 않는다.** 기술로 확인할 방법이 없다. 업로더가 무엇을 하고 있는지 자각하게 하는 것이 할 수 있는 전부다.

### 4.4 사전 고지

업로드 **전에** 데이터가 어떻게 다뤄지는지 알린다. 결과를 본 뒤에 알리면 늦다.

- 올린 이미지는 분석이 끝나는 즉시 삭제
- 결과는 20분 뒤 자동 삭제
- 계정도 기록도 없음
- 이용약관·개인정보 처리방침 링크

### 4.5 캡처에 남는 민감한 것

업로드 화면에 한 줄을 둔다.

> 캡처에 **전화번호·주소·계좌번호·사진**이 보이면 가리고 올려주세요.
> 대화 상대의 이름은 저희가 자동으로 지웁니다.

**부탁의 범위를 우리가 못 지우는 것에만 한정한다.** "개인정보를 가려주세요" 같은 넓은 부탁은 지켜지지 않는다. 재미로 써보는 서비스에서 캡처를 일일이 편집할 사람은 거의 없고, 지키지 않을 것을 알면서 넣는 고지는 면피용이 된다.

이름을 부탁하지 않는 이유는 **코드가 이미 지우기 때문이다**(`OCR-Parser-명세.md` 7.1). 부탁 대신 보장할 수 있는 것은 부탁하지 않는다. 그 사실을 함께 밝혀 무엇이 자동이고 무엇이 사용자 몫인지 가른다.

이 고지가 상대방 동의 문제를 해결하지는 않는다. 그것은 서비스 구조에서 나오는 위험이라 문구로 없앨 수 없다.

## 5. 진행 화면

### 5.1 폴링

- **서버가 준 `pollAfterSeconds` 를 따른다.** 클라이언트가 임의로 정하지 않는다.
- 값이 없으면 2초로 대신한다.
- 서버가 `done` 이면 결과를 받아온다. `failed` 면 오류를 표시한다.

### 5.2 진행률

`stage` 를 단계별 백분율에 대응시킨다.

| 단계 | 표시 | 진행률 |
| --- | --- | ---: |
| — (업로드 중) | 캡처를 올리는 중 | 8 |
| — (단계 미상) | 분석을 준비하는 중 | 12 |
| `ocr` | 대화를 읽는 중 | 20 |
| `parsing` | 메시지를 정리하는 중 | 35 |
| `analyzing` | 관계를 살펴보는 중 | 60 |
| `scoring` | 점수를 계산하는 중 | 75 |
| `reporting` | 리포트를 쓰는 중 | 90 |

**이 값은 실제 완료 비율이 아니다.** 목적은 정확한 예측이 아니라 "멈추지 않았다"를 보여주는 것이다. 단계를 모르는 동안에도 0%를 보여주지 않는다.

### 5.3 취소

두지 않는다. 분석은 수십 초면 끝나고, 취소 버튼은 사용자가 이탈로 해결할 수 있는 문제를 UI로 옮길 뿐이다. 이탈하면 삭제 요청이 나간다.

## 6. 결과 화면

### 6.1 표시 항목

| 항목 | 강조 |
| --- | --- |
| 친구비 | **가장 크게.** 서비스의 대표 지표다. 방향 문구와 함께 **블록으로 떼어 놓는다**(6.1.1) |
| 헤드라인 | 그다음 |
| 요약 | 본문 |
| 지표 6종 | 격자 |
| 리포트 단락 2~3개 | 본문 |
| 제안 | 강조 상자 |
| 메타 (메시지 수, 기간) | 작게 |
| 고지 문구 | 맨 아래, 반드시 |

#### 6.1.1 친구비 블록

친구비는 방향 문구와 금액을 한 블록에 담아 본문에서 떼어 놓는다.

```text
┌────────────────────────────┐
│ ▎친구에게 친구비를 주세요   │   ← 방향 문구. 금액의 뜻을 정한다
│ ▎79,000원                  │   ← 절댓값. 부호를 붙이지 않는다
└────────────────────────────┘
   └ 왼쪽 세로 바로 방향 표시
```

배경 없이 패널 위에 얹어두었더니 헤드라인·요약과 구분되지 않아 눈에 걸리지
않았다. 대표 지표이므로 한 덩어리로 뗀다.

방향 문구를 흐리게 두지 않는다. **이 줄이 금액의 뜻을 정한다.** 같은
`79,000원` 이 받을 돈일 수도 주어야 할 돈일 수도 있다.

방향은 왼쪽 세로 바의 색으로도 표시하되 **뜻은 문구가 말한다.** 색만으로
전하면 색을 구분하지 못하는 사용자에게는 아무 정보도 아니다.

**음수에 빨강을 쓰지 않는다.** 빨강은 '나쁨'으로 읽히는데 음수의 뜻은 "상대가
나보다 더 기여했다"이지 나쁜 관계가 아니다. 색까지 경고로 만들면 문구로 애써
푼 뜻이 도로 뒤집힌다.

방향 문구는 두 방향 모두 **할 일**로 쓴다. `요청하세요` / `주세요`. 한쪽만
설명하는 말이면 같은 자리에 번갈아 나올 때 결이 달라진다.

#### 6.1.2 지표 칸의 색

여섯 칸이 모두 같은 회색이라 눈이 갈 곳이 없었다. 숫자만 있고 **그 숫자가 좋은 쪽인지 나쁜 쪽인지** 알 길도 없었다. `손절 위험도 8점` 이 잘 나온 것인지 사용자는 모른다.

색으로 두 가지를 한꺼번에 푼다. 눈에 띄게 하고, 뜻을 알려준다.

| 톤 | 색 | 뜻 |
| --- | --- | --- |
| `good` | `--ok` (초록) | 좋은 쪽 |
| `warn` | `--accent` (노랑) | 중간 |
| `risk` | `--danger` (빨강) | 치우쳤거나 주의할 쪽 |
| `none` | 회색 | 좋고 나쁨이 없는 값 |

구간은 셋으로 나눈다.

```text
값을 먼저 '좋은 정도'로 뒤집는다. 그러면 기준이 하나뿐이다.

  높을수록 좋은 지표 (친밀도, 연락 균형도)  →  좋은 정도 = 값
  낮을수록 좋은 지표 (손절 위험도)          →  좋은 정도 = 100 - 값

  좋은 정도 60 이상  good     30~59  warn     29 이하  risk

방향마다 부등호를 따로 쓰면 경계에서 앞뒤가 어긋난다. 뒤집어 놓으면
손절 위험도는 자동으로 거울상이 된다 — 40 이하 good, 41~70 warn, 71 이상 risk.

균형 지표 (내가 먼저)
  0.5 에서 떨어진 거리로 잰다
  0.15 이하  good     0.30 이하  warn     그 밖  risk

답장 속도 (나, 상대)
  언제나 none. 빠른 답장이 좋은 관계라는 근거가 없다
```

세 칸으로 나눈 것은 사용자가 한눈에 읽을 수 있는 최대치이기 때문이다. 다섯 단계로 나누면 색이 다섯 가지가 되어 다시 구분이 안 된다.

경계를 삼등분(67/33)이 아니라 **60/30** 에 둔 것은 실측 때문이다. 친밀도 64, 연락 균형도 62 가 노랑으로 떨어졌는데, 둘 다 준수한 값이라 노랑이 어울리지 않았다. 60은 "그만하면 괜찮다"로 읽히는 선이다.

**답장 속도에 색을 주지 않는 이유**는 좋고 나쁨을 말할 근거가 없어서다. 빨리 답한다고 좋은 관계가 아니고 늦게 답한다고 나쁜 관계가 아니다. 근거 없는 판단을 색으로 전하지 않는다.

**여기서는 빨강을 쓴다.** 친구비에는 쓰지 않았다(6.1.1). 친구비의 부호는 '누가 더 기여했나'이지 좋고 나쁨이 아니지만, `손절 위험도` 는 **이름 그대로 위험도**다. 높으면 주의하라는 뜻이 맞다. 같은 색을 한쪽에서는 금지하고 다른 쪽에서는 쓰는 것이 아니라, **뜻이 다른 값이므로 다르게 칠한다.**

색은 값 글자와 칸 배경·테두리에 함께 준다. 값에만 주면 칸이 여전히 배경에 묻힌다.

**색만으로 뜻을 전하지 않는다.** 색을 구분하지 못하는 사용자에게는 아무 정보도 아니다. 숫자와 라벨이 그대로 있고, 색은 거드는 역할이다.

### 6.2 `null` 을 0으로 뭉개지 않는다

`avgReplySeconds` 는 표본이 부족하면 `null` 이다. 이때 **"알 수 없음"으로 표시한다.**

`0초`로 보이면 "즉시 답장하는 사이"라는 정반대의 뜻이 된다. 서버가 굳이 `null` 을 구분해 보내는 이유가 여기 있다.

### 6.3 없는 정밀도를 주장하지 않는다

**1분 미만은 초 단위로 표시하지 않는다.** "1분 이내"로 쓴다.

카카오톡 캡처의 시각은 **분 단위**다. 같은 분에 오간 메시지는 간격이 0초로 계산된다. 화면에 "0초"나 "45초"라고 쓰면 원본에 없던 정밀도를 주장하는 것이고, 사용자는 그것을 즉답으로 읽는다.

서버는 계산한 값을 초 단위로 그대로 준다. 어디까지 보여줄지는 화면이 정한다.

### 6.4 표본이 적을 때의 안내

**신뢰도 등급은 두지 않는다.** 재미로 읽는 결과에 정확도 등급을 붙이면 사용자는 그것을 자기 관계에 대한 평가로 읽는데, 실제로 등급을 끌어내리던 것은 관계가 아니라 우리 OCR 품질이었다(`관계-점수-계산-규칙.md` 11장).

대신 표본이 정말 적을 때만 한 줄을 띄운다.

```text
meta.messageCount < THIN_MESSAGES  →  분석한 대화가 적어 결과가 흔들릴 수 있어요
```

`THIN_MESSAGES` 는 **40**이다. 분석을 거절하는 하한(`MIN_MESSAGES` 15)과 다르다. 15~39개는 분석은 하되 결과를 곧이곧대로 읽지 말라고 알려주는 구간이다.

판단 근거를 `messageCount` 하나로 둔 이유는 그것이 **사용자가 어찌할 수 있는 값**이기 때문이다. 캡처를 더 올리면 늘어난다. 시각 복원 비율은 OCR 이 시각을 읽어내느냐에 달려 있어 사용자가 손댈 수 없다. 손댈 수 없는 값으로 경고를 띄우면 사용자는 무엇을 해야 할지 모른다.

`meta.sampled` 가 `true` 면 일부만 분석했다는 사실도 따로 알린다. 이쪽은 대화가 **너무 많아서** 생기는 일이라 뜻이 반대다.

### 6.5 결과 이미지 저장과 공유

**서버에 다운로드 엔드포인트가 없다.** 브라우저가 직접 그린다(기준 명세 11장).

- 캔버스에 직접 그린다. DOM 캡처 라이브러리를 쓰지 않는다.
- 이유: 의존성 없이 어느 브라우저에서나 같은 결과가 나온다. 폰트 로딩이나 CSS 해석 차이로 이미지가 깨지지 않는다.
- 카드에는 친구비, 지표 6종, 헤드라인, 요약, **고지 문구**를 담는다.
- 실패하면 "화면을 캡처해 주세요"로 안내한다. 조용히 아무 일도 일어나지 않게 두지 않는다.

**저장과 공유는 목적이 다르므로 버튼을 나눈다.** 저장은 내가 가져가는 것이고
공유는 남에게 보내는 것이다. 하나로 합쳐 "결과 이미지 저장"이라고만 쓰면
공유가 되는 줄 모른다.

| 버튼 | 담는 것 |
| --- | --- |
| 친구에게 공유 (주) | 이미지 + 방향 문구 + **서비스 링크** |
| 결과 이미지 저장 (보조) | 이미지만 |

공유는 세 단계로 물러선다.

```text
1. 파일 + 문구 + 링크 공유
2. 파일이 거절되면 문구 + 링크만 공유
     데스크톱 브라우저는 파일 공유를 자주 거절한다.
     여기서 포기하면 링크가 친구에게 가지 않는다
3. 공유 자체가 없으면 링크를 클립보드에 복사하고 이미지는 내려받는다
```

이미지를 만들지 못해도 링크 공유는 계속한다. 이미지가 없다고 공유를 포기하면
친구는 아무것도 받지 못한다.

**링크는 결과가 아니라 서비스 첫 화면을 가리킨다.** 11장의 "결과 공유 링크를
두지 않는다"는 결정은 그대로다. 친구에게 필요한 것은 내 결과 열람이 아니라
"너도 해봐"다.

도메인을 박아두지 않고 `window.location.origin` 을 쓴다. 박아두면 배포 주소가
바뀔 때 조용히 틀린 링크를 뿌린다.

### 6.6 TTL 카운트다운

`expiresAt` 까지 남은 시간을 초 단위로 보여준다.

만료되면 문구를 바꾼다.

> 결과가 서버에서 삭제되었어요. 저장한 이미지는 그대로 남아 있습니다.

사용자가 손해를 봤다고 느끼지 않게 하는 것이 목적이다. 실제로 저장한 이미지는 남아 있다.

## 7. 실패 화면

### 7.1 오류 코드마다 다른 안내

`error.code` 로 분기한다. **원인마다 사용자가 할 수 있는 일이 다르기 때문이다.**

| 코드 | 다시 시도 권유 |
| --- | --- |
| `TOO_FEW_MESSAGES` | **하지 않는다.** 같은 캡처로는 같은 결과다 |
| `NO_CONVERSATION_FOUND` | 하지 않는다 |
| `GROUP_CHAT_DETECTED` | 하지 않는다 |
| `SPEAKER_DETECTION_FAILED` | 하지 않는다 |
| `IMAGE_*` | 하지 않는다 |
| `DAILY_LIMIT_EXCEEDED` | 하지 않는다 |
| `JOB_EXPIRED` | 하지 않는다 |
| `RATE_LIMITED` | 한다 |
| `CONCURRENCY_LIMIT` | 한다 |
| `ANALYSIS_TIMEOUT` | 한다 |
| `NETWORK_ERROR` | 한다 |
| 그 밖 | `retryable` 을 따른다 |

대화가 짧아 실패한 사람에게 "다시 시도"를 권하면 같은 결과만 반복된다. 무엇을 고쳐야 하는지 알려주는 편이 낫다.

### 7.2 모르는 코드

서버가 새 오류 코드를 추가해도 화면이 깨지지 않아야 한다. 기본 안내를 보여주고 `retryable` 을 따른다.

### 7.3 오류 코드 노출

문의에 쓸 수 있도록 코드를 작게 표시한다. 다만 `jobId` 는 노출하지 않는다.

## 8. 임시 데이터 정리

클라이언트도 삭제 책임을 진다.

| 시점 | 동작 |
| --- | --- |
| "다른 대화 분석하기" | `DELETE /v1/analyses/{jobId}` |
| 페이지 이탈 (`pagehide`) | `sendBeacon` 으로 `POST .../deletion` |
| 컴포넌트 언마운트 | 같음 |

`sendBeacon` 을 쓰는 이유는 **이탈 중에는 일반 요청이 취소되기 때문**이다. `sendBeacon` 은 POST만 보낼 수 있어서 서버가 별도 경로를 열어 두었다.

**삭제 요청이 실패해도 사용자에게 알리지 않는다.** 도달하지 못하면 서버의 TTL이 대신 지운다. 떠나는 사람에게 오류를 띄울 이유가 없다.

## 9. 접근성

| 항목 | 처리 |
| --- | --- |
| 진행률 | `role="progressbar"` 와 `aria-valuenow` |
| 이미지 제거 버튼 | `aria-label` 로 몇 번째인지 알림 |
| 미리보기 이미지 | 순번을 담은 `alt`. 빈 `alt` 를 쓰지 않는다 |
| 장식 요소 | `aria-hidden` |
| 애니메이션 | `prefers-reduced-motion` 존중 |
| 색상 | 어두운 배경 기준. 대비 확보 |

미리보기 이미지에 빈 `alt` 를 쓰지 않는 이유는, 그것이 **어떤 캡처를 골랐는지 알려주는 의미 있는 정보**이기 때문이다. 장식이 아니다.

## 11. 하지 않는 것

의도적으로 넣지 않은 것들이다. 나중에 "왜 없지?"라는 질문에 답하기 위해 적어둔다.

- **결과 공유 링크**: 서버에 결과가 20분만 있고, 링크를 아는 사람이 열 수 있게 되어 개인정보 위험이 생긴다.
  **서비스 첫 화면 링크를 공유하는 것은 다른 이야기다**(6.5). 그쪽은 남의 결과를 열지 않는다
- **분석 이력**: 기준 명세 3장의 제외 항목
- **로그인**: 같음
- **다크/라이트 전환**: 어두운 테마로 고정. 결과 카드 색과 맞추기 위해서다
- **다국어**: 카카오톡 한국어 대화가 대상이다
- **취소 버튼**: 5.3 참조
