## 1. 문서 목적

이 문서는 업로드된 대화 캡처 이미지를 `ConversationData`로 변환하는 규칙을 정의한다. 담당 범위는 OCR 호출부터 Parser 출력까지이며, 그 이후 단계는 다루지 않는다.

## 2. OCR 엔진 요구사항

**엔진 선정의 1순위 기준은 정확도가 아니라 좌표 제공 여부다.**

| 요구사항 | 필수 여부 | 이유 |
| --- | --- | --- |
| 텍스트별 bounding box 좌표 반환 | **필수** | 좌우 위치로 화자를 판별한다. 좌표가 없으면 서비스의 지표 절반이 계산 불가능해진다 |
| 이미지 원본 크기(width, height) 반환 | **필수** | 좌표를 상대 위치로 환산하는 기준값 |
| 한국어 인식 | **필수** | 대상 사용자가 한국어 대화를 올린다 |
| 블록 단위 신뢰도 | 권장 | 저신뢰 블록 제외에 사용 |
| 줄 단위 분할 | 권장 | 없으면 Parser에서 y 좌표로 직접 나눈다 |

좌표를 반환하지 않는 엔진, 또는 텍스트를 한 덩어리 문자열로만 주는 엔진은 **후보에서 제외한다.**

## 3. OCR 산출물

OCR 단계는 이미지 한 장당 `OcrPage` 하나를 만든다. 구조 정의는 `데이터-계약-명세.md` 4장에 있다.

```json
{
  "imageIndex": 0,
  "width": 1080,
  "height": 2340,
  "blocks": [
    { "text": "내일 시간 돼?", "box": { "x": 612, "y": 830, "w": 396, "h": 44 }, "confidence": 0.97 }
  ]
}
```

`confidence`가 0.5 미만인 블록은 폐기하고 `droppedCount`에 반영한다.

## 4. 화자 판별

### 4.1 판별 규칙

카카오톡 1:1 화면에서 내 메시지는 **오른쪽 끝**에, 상대 메시지는 **왼쪽 끝**에 붙는다. 이 정렬을 좌표로 읽는다.

각 블록에 대해 좌우 여백을 구한다.

```text
leftMargin  = box.x
rightMargin = page.width - (box.x + box.w)

leftMargin  < rightMargin  →  speaker = "peer"
rightMargin < leftMargin   →  speaker = "me"
```

**블록의 중심점이 아니라 여백을 비교한다.** 긴 메시지는 화면 폭의 70% 이상을 차지해서 중심점이 화면 중앙 근처로 몰린다. 여백 비교는 메시지 길이와 무관하게 동작한다.

### 4.2 판별 불가 처리

```text
|leftMargin - rightMargin| < page.width × 0.05  →  중앙 정렬로 간주
```

중앙 정렬 블록은 날짜 구분선, 시스템 안내, 공지다. 메시지로 취급하지 않고 별도로 분류한다(6장 참조).

한 이미지에서 좌우 어느 쪽으로도 판별된 블록이 **전혀 없으면** `SPEAKER_DETECTION_FAILED`로 처리한다.

### 4.3 블록 병합

한 말풍선이 여러 줄로 나뉘어 별도 블록으로 반환될 수 있다. 아래 조건을 모두 만족하면 같은 메시지로 병합한다.

- 같은 `imageIndex`
- 같은 판별 화자
- y 간격이 앞 블록 높이(`box.h`)의 **0.4배 이내**
- 좌우 정렬 기준선이 유사 (`me`는 `rightMargin` 차이, `peer`는 `leftMargin` 차이가 `page.width × 0.03` 이내)

병합 시 텍스트는 줄바꿈 없이 공백 하나로 잇는다.

**세로 간격 허용치를 좁게 잡는 이유**가 있다. 말풍선 안에서 줄이 바뀔 때의 간격은 거의 0에 가깝지만, 별개 메시지 사이에는 여백이 들어간다. 이 차이가 두 경우를 가르는 유일한 단서다.

허용치를 넓게 잡으면 **서로 다른 메시지가 한 덩어리로 합쳐진다.** 그러면 메시지 수가 줄어 연락 균형도와 답장 속도가 통째로 틀어지는데, 결과는 그럴듯하게 나오므로 알아채기 어렵다.

실제 엔진을 붙인 뒤 말풍선이 잘게 쪼개져 나오면 이 값을 올린다. 반대로 별개 메시지가 붙어 나오면 내린다. 판단 근거는 `--review` 로 뽑은 검토 파일이다.

### 4.4 정렬 순서

`imageIndex` 오름차순 → 같은 이미지 안에서는 `box.y` 오름차순.

캡처는 위에서 아래로 시간이 흐르고, 이미지는 업로드 순서가 곧 시간 순서라고 가정한다. 이 가정이 깨지면(사용자가 순서를 뒤섞어 올림) 시간 복원 단계에서 시각 역행으로 드러난다.

## 5. 시간 복원

### 5.1 인식 패턴

| 대상 | 패턴 예시 |
| --- | --- |
| 시각 | `오전 9:15`, `오후 11:50`, `21:15` |
| 날짜 구분선 | `2026년 8월 25일`, `2026년 8월 25일 화요일`, `2026. 8. 25.` |

시각 블록은 말풍선 옆에 작게 붙는다. `box.y` 중심이 가장 가까운 메시지에 귀속시킨다.

### 5.2 날짜 앵커

날짜 구분선(중앙 정렬 블록)을 만나면 이후 메시지의 **기준 날짜**를 그 값으로 갱신한다.

```text
날짜 구분선 발견 → anchorDate 갱신
메시지 시각 + anchorDate → sentAt (timeSource = "explicit")
```

**앵커는 이미지 경계를 넘어 이어진다.** 시각 복원은 이미지별로 하지 않고, 모든 이미지를 시간순으로 이어 붙인 하나의 흐름 위에서 한 번에 수행한다.

스크롤 캡처는 한 대화를 잘라놓은 것이고, 날짜 구분선은 보통 첫 화면에만 찍힌다. 이미지마다 앵커를 초기화하면 두 번째 이미지부터 가상 기준일(5.4)로 되돌아가 **시간이 거꾸로 흐른다.** 그러면 세션 분할과 답장 간격이 통째로 무너진다.

따라서 날짜 구분선은 폐기하되 **위치를 지키는 표식으로 남겨** 두었다가, 이어 붙인 흐름을 훑으면서 만나는 순서대로 앵커를 갱신한다. 화면 중간에서 날짜가 바뀌는 경우도 이렇게 처리된다.

### 5.3 자정 넘김 보정

같은 앵커 구간 안에서 시각이 역행하면 날짜가 넘어간 것으로 본다.

```text
직전 메시지 22:50 → 현재 메시지 00:15
  → 현재 메시지의 날짜를 +1일
  → timeSource = "inferred"
```

### 5.4 앵커가 없는 경우

캡처에 날짜 구분선이 한 번도 나오지 않을 수 있다. 이때는 **가상 타임라인**을 구성한다.

- 첫 메시지를 기준일 00:00 이후 첫 시각으로 배치한다.
- 이후 메시지는 시각과 자정 넘김 보정만으로 상대 배치한다.
- 모든 메시지의 `timeSource`는 `inferred`다.

이 경우 `sentAt`의 **절대 날짜는 의미가 없고 간격만 유효하다.** 점수 계산에 쓰이는 값은 답장 간격과 세션 구분뿐이므로 문제가 없다. 절대 시각은 API 응답에 노출되지 않는다(`데이터-계약-명세.md` 12장).

### 5.5 복원 실패

시각 블록이 없거나 패턴에 맞지 않으면 `sentAt = null`, `timeSource = "unknown"`으로 둔다. 이 메시지는 답장 간격 수집과 세션 분할에서 제외된다.

## 6. 중앙 정렬 블록 처리

| 유형 | 판별 | 처리 |
| --- | --- | --- |
| 날짜 구분선 | 5.1의 날짜 패턴 일치 | 앵커로 사용 후 폐기 |
| 시스템 안내 | `님이 들어왔습니다`, `님이 나갔습니다`, `삭제된 메시지입니다` 등 | 폐기, `droppedCount` 증가 |
| 그 밖 | — | 폐기, `droppedCount` 증가 |

## 7. 단체 대화방 감지

이 서비스는 **1:1 대화만 지원한다.**

카카오톡 단체방은 왼쪽 말풍선 위에 발신자 이름 라벨이 붙는다. 1:1 대화에는 이 라벨이 없다.

```text
왼쪽 정렬 블록의 바로 위(y 간격 < box.h × 1.2)에 위치하고
폰트 높이가 말풍선 블록보다 작은 짧은 텍스트를 이름 라벨로 수집

서로 다른 이름 라벨이 2개 이상  →  GROUP_CHAT_DETECTED
```

감지 시 분석을 중단하고 오류를 반환한다.

## 8. 텍스트 정규화

정규화의 목적은 두 가지다. 하나는 LLM 입력 토큰을 줄이는 것이고, 다른 하나는 의미 없는 변형을 제거해 분석 품질을 높이는 것이다.

| 규칙 | 변환 전 | 변환 후 |
| --- | --- | --- |
| 반복 문자 축약 (3회 초과 → 2회) | `ㅋㅋㅋㅋㅋㅋㅋ` | `ㅋㅋ` |
| 반복 기호 축약 | `!!!!!!` | `!!` |
| URL 치환 | `https://...` | `[링크]` |
| 사진 표기 | `사진`, `사진 3장` | `[사진]` |
| 이모티콘 표기 | `이모티콘` | `[이모티콘]` |
| 동영상 표기 | `동영상` | `[동영상]` |
| 파일 표기 | `파일: xxx.pdf` | `[파일]` |
| 연속 공백 | `안녕    하세요` | `안녕 하세요` |

정규화 후 빈 문자열이 되는 메시지는 제거하고 `droppedCount`를 증가시킨다.

반복 문자 축약은 감정 강도 정보를 일부 잃지만, `ㅋ`가 30번 반복되는 메시지 하나가 토큰 수십 개를 먹는 비용이 더 크다. 강도는 반복 여부(2회로 축약되었는지)로 남는다.

## 9. 이미지 간 중복 제거

스크롤 캡처는 인접 이미지의 경계가 겹친다. 이 구간을 제거하지 않으면 메시지 수가 부풀려져 모든 비율 지표가 왜곡된다.

```text
K = 10

for i in 0..n-2:
    tail = 이미지 i의 마지막 K개 메시지
    head = 이미지 i+1의 처음 K개 메시지

    (speaker, 정규화된 text) 쌍이 3개 이상 연속 일치하는
    가장 긴 구간을 찾는다

    발견되면 이미지 i+1에서 그 구간을 제거한다
```

3개 연속을 기준으로 삼은 이유는, 짧은 메시지(`ㅇㅇ`, `ㅋㅋ`)는 우연히 일치할 수 있어서 1~2개 일치로는 오탐이 나기 때문이다.

## 10. 샘플링

직렬화된 `ConversationData`의 예상 토큰이 설정된 상한을 넘으면 메시지를 추려낸다.

```text
상한 초과 시:
  앞부분 30개  (관계의 초기 맥락)
  뒷부분 50개  (현재 상태)
  중간 40개    (남은 구간에서 균등 간격 추출)
  = 총 120개

meta.sampled = true
```

뒷부분을 앞부분보다 많이 남기는 이유는, 관계의 **현재 상태**가 판단에 더 중요하기 때문이다. 손절 위험도와 답장 속도는 최근 데이터가 결정한다.

샘플링이 발생하면 `confidence`가 한 단계 강등된다(`관계-점수-계산-규칙.md` 11장).

**샘플링은 메시지를 잘라내는 것이지 LLM 호출을 나누는 것이 아니다.** 기준 명세의 LLM 1회 호출 원칙은 유지된다.

## 11. 최소 요건 검증

Parser 출력 직전에 검사한다.

| 조건 | 결과 |
| --- | --- |
| `messageCount < 15` | `TOO_FEW_MESSAGES` |
| `speaker`가 한쪽만 존재 | `NO_CONVERSATION_FOUND` |
| 유효 블록이 0개 | `NO_CONVERSATION_FOUND` |

## 12. 실패 처리 매핑

| 상황 | 오류 코드 |
| --- | --- |
| OCR 엔진 호출 실패·타임아웃 | `OCR_FAILED` |
| 인식된 텍스트 블록이 없음 | `NO_CONVERSATION_FOUND` |
| 좌우 판별된 블록이 전혀 없음 | `SPEAKER_DETECTION_FAILED` |
| 서로 다른 이름 라벨 2개 이상 | `GROUP_CHAT_DETECTED` |
| 정규화 후 메시지 15개 미만 | `TOO_FEW_MESSAGES` |
| 한쪽 화자만 존재 | `NO_CONVERSATION_FOUND` |

오류 메시지에 **대화 원문, 파일명, 좌표를 포함하지 않는다.**

## 13. 로깅 제약

기준 명세 5장에 따라 아래를 로그에 남기지 않는다.

- 대화 원문 텍스트 (정규화 전후 모두)
- OCR 블록의 `text` 필드
- 업로드 파일명

남길 수 있는 것은 블록 수, 메시지 수, 제거 건수, 처리 시간, 오류 코드 같은 **집계값과 식별자뿐이다.**

## 14. 검증 항목

OCR 엔진 후보를 평가할 때 아래를 실제 카카오톡 캡처로 측정한다.

| 항목 | 기준 |
| --- | --- |
| 화자 판별 정확도 | 좌우 판별이 틀린 메시지 비율 |
| 시각 인식률 | `timeSource`가 `unknown`이 아닌 비율 |
| 텍스트 정확도 | 한글 오인식률 |
| 처리 시간 | 이미지 1장당 소요 시간 |
| 건당 비용 | 이미지 1장당 과금액 |

기준 명세 8장에 따라 저비용 방식을 먼저 검증하되, **화자 판별 정확도가 기준에 못 미치면 비용이 낮아도 채택하지 않는다.** 이 지표가 틀리면 결과 전체가 틀린다.
