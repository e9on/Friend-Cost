## 1. 문서 목적

이 문서는 업로드된 대화 캡처 이미지를 `ConversationData`로 변환하는 규칙을 정의한다. 담당 범위는 OCR 호출부터 Parser 출력까지이며, 그 이후 단계는 다루지 않는다.

## 2. OCR 엔진 요구사항

**엔진 선정의 1순위 기준은 정확도가 아니라 좌표 제공 여부다.**

| 요구사항 | 필수 여부 | 이유 |
| --- | --- | --- |
| 텍스트별 bounding box 좌표 반환 | **필수** | 좌우 위치로 화자를 판별한다. 좌표가 없으면 서비스의 지표 절반이 계산 불가능해진다 |
| 이미지 원본 크기(width, height) 반환 | **필수** | 좌표를 상대 위치로 환산하는 기준값 |
| 한국어 인식 | **필수** | 대상 사용자가 한국어 대화를 올린다 |
| 블록 단위 신뢰도 | 권장 | 저신뢰 블록 제외에 사용 |
| 줄 단위 분할 | 권장 | 없으면 Parser에서 y 좌표로 직접 나눈다 |

좌표를 반환하지 않는 엔진, 또는 텍스트를 한 덩어리 문자열로만 주는 엔진은 **후보에서 제외한다.**

## 3. OCR 산출물

OCR 단계는 이미지 한 장당 `OcrPage` 하나를 만든다. 구조 정의는 `데이터-계약-명세.md` 4장에 있다.

```json
{
  "imageIndex": 0,
  "width": 1080,
  "height": 2340,
  "blocks": [
    { "text": "내일 시간 돼?", "box": { "x": 612, "y": 830, "w": 396, "h": 44 }, "confidence": 0.97 }
  ]
}
```

`confidence`가 0.5 미만인 블록은 폐기하고 `droppedCount`에 반영한다.

## 4. 화자 판별

### 4.1 판별 규칙

카카오톡 1:1 화면에서 내 메시지는 **오른쪽 끝**에, 상대 메시지는 **왼쪽 끝**에 붙는다. 이 정렬을 좌표로 읽는다.

각 블록에 대해 좌우 여백을 구한다.

```text
leftMargin  = box.x
rightMargin = page.width - (box.x + box.w)

leftMargin  < rightMargin  →  speaker = "peer"
rightMargin < leftMargin   →  speaker = "me"
```

**블록의 중심점이 아니라 여백을 비교한다.** 긴 메시지는 화면 폭의 70% 이상을 차지해서 중심점이 화면 중앙 근처로 몰린다. 여백 비교는 메시지 길이와 무관하게 동작한다.

### 4.2 판별 불가 처리

```text
|leftMargin - rightMargin| < page.width × 0.05  →  중앙 정렬로 간주
```

중앙 정렬 블록은 날짜 구분선, 시스템 안내, 공지다. 메시지로 취급하지 않고 별도로 분류한다(6장 참조).

한 이미지에서 좌우 어느 쪽으로도 판별된 블록이 **전혀 없으면** `SPEAKER_DETECTION_FAILED`로 처리한다.

### 4.3 블록 병합

한 말풍선이 여러 줄로 나뉘어 별도 블록으로 반환될 수 있다. 아래 조건을 모두 만족하면 같은 메시지로 병합한다.

- 같은 `imageIndex`
- 같은 판별 화자
- y 간격이 앞 블록 높이(`box.h`)의 **0.4배 이내**
- 좌우 정렬 기준선이 유사 (`me`는 `rightMargin` 차이, `peer`는 `leftMargin` 차이가 `page.width × 0.03` 이내)

병합 시 텍스트는 줄바꿈 없이 공백 하나로 잇는다.

**세로 간격 허용치를 좁게 잡는 이유**가 있다. 말풍선 안에서 줄이 바뀔 때의 간격은 거의 0에 가깝지만, 별개 메시지 사이에는 여백이 들어간다. 이 차이가 두 경우를 가르는 유일한 단서다.

허용치를 넓게 잡으면 **서로 다른 메시지가 한 덩어리로 합쳐진다.** 그러면 메시지 수가 줄어 연락 균형도와 답장 속도가 통째로 틀어지는데, 결과는 그럴듯하게 나오므로 알아채기 어렵다.

실제 엔진을 붙인 뒤 말풍선이 잘게 쪼개져 나오면 이 값을 올린다. 반대로 별개 메시지가 붙어 나오면 내린다. 판단 근거는 `--review` 로 뽑은 검토 파일이다.

### 4.4 정렬 순서

`imageIndex` 오름차순 → 같은 이미지 안에서는 `box.y` 오름차순.

캡처는 위에서 아래로 시간이 흐르고, 이미지는 업로드 순서가 곧 시간 순서라고 가정한다. 이 가정이 깨지면(사용자가 순서를 뒤섞어 올림) 시간 복원 단계에서 시각 역행으로 드러난다.

## 5. 시간 복원

### 5.1 인식 패턴

| 대상 | 패턴 예시 |
| --- | --- |
| 시각 | `오전 9:15`, `오후 11:50`, `21:15` |
| 날짜 구분선 | `2026년 8월 25일`, `2026년 8월 25일 화요일`, `2026. 8. 25.` |

시각 블록은 말풍선 옆에 작게 붙는다. `box.y` 중심이 가장 가까운 메시지에 귀속시킨다.

### 5.2 날짜 앵커

날짜 구분선(중앙 정렬 블록)을 만나면 이후 메시지의 **기준 날짜**를 그 값으로 갱신한다.

```text
날짜 구분선 발견 → anchorDate 갱신
메시지 시각 + anchorDate → sentAt (timeSource = "explicit")
```

**앵커는 이미지 경계를 넘어 이어진다.** 시각 복원은 이미지별로 하지 않고, 모든 이미지를 시간순으로 이어 붙인 하나의 흐름 위에서 한 번에 수행한다.

스크롤 캡처는 한 대화를 잘라놓은 것이고, 날짜 구분선은 보통 첫 화면에만 찍힌다. 이미지마다 앵커를 초기화하면 두 번째 이미지부터 가상 기준일(5.4)로 되돌아가 **시간이 거꾸로 흐른다.** 그러면 세션 분할과 답장 간격이 통째로 무너진다.

따라서 날짜 구분선은 폐기하되 **위치를 지키는 표식으로 남겨** 두었다가, 이어 붙인 흐름을 훑으면서 만나는 순서대로 앵커를 갱신한다. 화면 중간에서 날짜가 바뀌는 경우도 이렇게 처리된다.

### 5.3 자정 넘김 보정

같은 앵커 구간 안에서 시각이 역행하면 날짜가 넘어간 것으로 본다.

```text
직전 메시지 22:50 → 현재 메시지 00:15
  → 현재 메시지의 날짜를 +1일
  → timeSource = "inferred"
```

### 5.4 앵커가 없는 경우

캡처에 날짜 구분선이 한 번도 나오지 않을 수 있다. 이때는 **가상 타임라인**을 구성한다.

- 첫 메시지를 기준일 00:00 이후 첫 시각으로 배치한다.
- 이후 메시지는 시각과 자정 넘김 보정만으로 상대 배치한다.
- 모든 메시지의 `timeSource`는 `inferred`다.

이 경우 `sentAt`의 **절대 날짜는 의미가 없고 간격만 유효하다.** 점수 계산에 쓰이는 값은 답장 간격과 세션 구분뿐이므로 문제가 없다. 절대 시각은 API 응답에 노출되지 않는다(`데이터-계약-명세.md` 12장).

### 5.5 앵커가 중간부터 나오는 경우

스크롤 캡처에서 흔하다. 위로 올려 찍은 화면에는 날짜 구분선이 없고 아래쪽
화면에만 있다.

앞쪽을 가상 기준일(5.4)에 두고 뒤쪽을 실제 날짜에 두면 **한 대화 안에 26년
간격이 생긴다.** 2026-08-27 실측에서 실제로 그랬다. 캡처 5장 중 앞 3장에
구분선이 없어 `spanSeconds` 가 8.4억 초, 곧 **318개월**로 나왔다.

첫 앵커 이전 메시지는 **첫 앵커 날짜에서 거꾸로 이어 붙인다.**

```text
첫 앵커 날짜 D 를 만나면
  그 앞 묶음의 마지막 메시지를 D - 1일에 놓고
  묶음 안의 간격(자정 넘김 포함)은 그대로 둔 채 통째로 옮긴다

timeSource 는 inferred 다. 날짜를 우리가 정했기 때문이다
```

D 가 아니라 **D − 1일**인 이유는 날짜 구분선이 `D` 의 **시작**을 뜻하기
때문이다. 구분선 바로 앞 메시지는 `D` 보다 앞선 날짜다.

이 값은 추정이다. 사용자가 한 달을 건너뛰어 캡처했다면 실제 간격은 더 크다.
그래도 5.4 가 이미 "절대 날짜는 의미가 없고 간격만 유효하다"고 한 범위 안이고,
묶음 **안쪽**의 간격은 정확히 보존된다. 답장 속도와 세션 분할은 그 안쪽 간격만
쓴다.

### 5.6 복원 실패

시각 블록이 없거나 패턴에 맞지 않으면 `sentAt = null`, `timeSource = "unknown"`으로 둔다. 이 메시지는 답장 간격 수집과 세션 분할에서 제외된다.

## 7. 단체 대화방 감지

이 서비스는 **1:1 대화만 지원한다.**

카카오톡은 왼쪽 말풍선 위에 발신자 이름 라벨을 붙인다. **1:1 대화에도 붙는다.**
이 문서는 처음에 "1:1 에는 라벨이 없다"고 적었는데, 실제 캡처에서 틀렸음이 드러났다(7.3).

그래서 판정 기준은 라벨이 **있느냐**가 아니라 **서로 다른 이름이 둘 이상이냐**이다.

```text
왼쪽 정렬 블록 중
  길이 <= NAME_LABEL_MAX_LEN 이고
  시각 라벨이 아니며
  바로 아래(y 간격 < box.h × NAME_LABEL_GAP_FACTOR)에 더 높은 블록이 있고
  그 아래 블록보다 x 가 이미지 폭 × NAME_LABEL_INDENT_RATIO 이상 왼쪽인 것
을 이름 후보로 모은다. **모든 이미지를 합쳐서** 센다.

같은 텍스트가 NAME_LABEL_MIN_REPEATS 회 이상 나타나면 이름 라벨로 본다.

이름 라벨끼리 유사도가 NAME_LABEL_SIMILARITY 이상이면 **같은 이름으로 합친다.**
OCR 은 같은 라벨을 매번 다르게 읽으므로 텍스트 완전 일치로 세면 한 사람이
여러 사람이 된다(7.3).

합친 뒤 남은 이름이 2개 이상  →  GROUP_CHAT_DETECTED
```

감지 시 분석을 중단하고 오류를 반환한다.

### 7.1 왜 폰트 높이로 가르지 않는가

이 문서는 처음에 "폰트 높이가 말풍선 블록보다 작은" 것을 이름으로 보라고 적었다. **2026-08-26 실측에서 그 기준이 무너졌다.**

합성 캡처로 1:1과 단체방을 각각 만들어 후보의 높이비를 재봤다.

| 캡처 | 높이비 분포 |
| --- | --- |
| 1:1 (전부 오탐이어야 한다) | 0.61 ~ 0.98 |
| 단체방 (전부 진짜 이름) | 0.82 ~ 0.97 |

**완전히 겹친다.** OCR 상자의 높이는 글꼴 크기가 아니라 받침과 윗선이 있는지를 따라간다. "그래"와 "김민지"는 글꼴이 같아도 상자 높이가 다르다.

높이만 믿으면 **"나 지금 회사야" 같은 평범한 메시지가 발신자 이름으로 오인된다.**

높이가 아니라 **x** 를 보면 갈린다. 7.4 에서 다룬다. 실측에서 실제로 그랬고, 그 결과 정상 1:1 대화가 `GROUP_CHAT_DETECTED` 로 거부됐다. 사용자에게는 서비스 거부로 보인다.

### 7.2 반복 횟수로 가르는 이유

발신자 이름은 그 사람이 말할 때마다 다시 붙는다. 그래서 **같은 텍스트가 반복된다.**

아래 수치는 `render_kakao.py` 로 그린 **합성** 캡처에서 잰 것이다. 합성 1:1 에는
이름 라벨을 그리지 않았으므로 "1:1 후보"는 전부 본문 오탐이다. 실제 1:1 에는
라벨이 붙는다(7.3).

| 캡처 | 후보 수 | 서로 다른 텍스트 | 최다 반복 |
| --- | ---: | ---: | --- |
| 1:1 | 9 | 8 | `그래조심히와` 2회 |
| 단체방 | 19 | 8 | `박준서` 5회, `김민지` 4회 |

`NAME_LABEL_MIN_REPEATS` 를 3으로 두면 1:1에서는 이름이 하나도 잡히지 않고 단체방에서는 둘이 잡힌다.

**이미지 한 장 안에서 세면 안 된다.** 이름은 여러 장에 흩어져 나타난다. 장당으로 세면 3회를 채우지 못해 단체방을 놓친다.

한계도 분명하다. **각자 한두 번만 말한 단체방은 놓친다.** 그 경우 1:1로 보고 분석하므로 결과가 엉뚱해진다. 오탐(정상 대화를 거부)과 미탐(단체방을 분석) 중 어느 쪽이 나쁜지는 판단의 문제이고, 여기서는 **거부를 더 나쁘게 본다.** 짧은 답장은 실제 대화에서 매우 흔하기 때문이다.

### 7.3 왜 텍스트 완전 일치로 세지 않는가

**2026-08-27 실제 캡처에서 정상 1:1 대화가 단체방으로 거부됐다.**

캡처 5장을 RapidOCR 에 넣었더니 왼쪽 라벨 자리(x≈99, w≈165, h≈32, 화면당 6~7회)
에서 이런 텍스트들이 나왔다.

```text
공어고글를렁을 (3회)   어고글를렁을 (4회)   허어고글를렁을   궁오고글를바을 …
```

전부 **같은 라벨** 하나다. 원문은 상대방 닉네임 `하트를 든 라이언` 이고,
어두운 배경에 JPEG 압축이 겹쳐 OCR 이 매번 다르게 읽었다. 신뢰도는 0.52~0.74 로
`MIN_BLOCK_CONFIDENCE` 를 모두 통과한다. **오인식은 신뢰도로 걸러지지 않는다.**

두 변형이 각각 3회를 넘겼고, 완전 일치로 세니 서로 다른 이름 2개가 되어
`GROUP_CHAT_DETECTED` 가 났다.

두 사실이 함께 드러났다.

1. **1:1 에도 이름 라벨이 붙는다.** 이 문서의 전제가 틀렸다. 다만 판정식은
   "서로 다른 이름 2개 이상"이었으므로 규칙 자체는 살아 있었다.
2. **같은 이름이 여러 철자로 갈라진다.** 이쪽이 결함이다.

임계값은 실측으로 정했다.

| 쌍 | 유사도 |
| --- | ---: |
| 합쳐야 하는 것 — 실제 오판정의 두 라벨 | 0.923 |
| 합치면 안 되는 것 — `김민지` / `김민수` | 0.667 |
| 합치면 안 되는 것 — `이서연` / `이서현` | 0.667 |
| 합치면 안 되는 것 — `김민지영` / `김민지수` | 0.750 |
| 합치면 안 되는 것 — 합성 단체방의 서로 다른 이름 전부 | 0.000 |

`NAME_LABEL_SIMILARITY` 를 **0.8** 로 둔다. 합치면 안 되는 쪽의 최댓값 0.750 과
합쳐야 하는 쪽의 0.923 사이다. 가운데(0.836)보다 낮게 잡은 것은 7.2 와 같은
이유다. **거부가 미탐보다 나쁘다.**

유사도는 `difflib.SequenceMatcher` 비율이다. 묶기는 단일 연결(single linkage)로,
한 쌍이라도 임계값을 넘으면 같은 이름으로 본다.

한계도 적어둔다. **이름이 서로 매우 비슷한 단체방은 놓친다.** `김민지영` 과
`김민지수` 는 0.750 이라 갈리지만, 한 글자 차이인 네 글자 이름이 더 붙어 있으면
합쳐진다. 그 경우 1:1 로 보고 분석한다.

### 7.4 왜 x 로 가르는가

7.1 은 **높이**로 가를 수 없다고 했다. 맞다. 그런데 **x 는 갈린다.**

이름 라벨은 프로필 사진 옆 여백선에 맞춰 그려지고, 말풍선은 그보다 안쪽에서
시작한다. 본문은 말풍선 안이므로 여백만큼 더 밀린다. 그래서 이름 라벨은
자기가 이름표를 붙인 말풍선보다 **왼쪽으로 튀어나온다.**

반면 본문끼리는 같은 말풍선 기준선을 쓰므로 x 가 같다. 짧은 메시지 다음에 긴
메시지가 와도 둘의 x 는 같다. 이것이 "나 지금 회사야"류 오탐을 자격 단계에서
잘라내는 근거다.

네 벌로 실측했다. 값은 아래 블록의 x 에서 후보의 x 를 뺀 것이다.

| 캡처 | 폭 | 진짜 이름 라벨 | 이름이 아닌 후보 |
| --- | ---: | ---: | ---: |
| 실제 1:1 (2026-08-27 오판정 건) | 720 | +15 ~ +21 | ≤ 0 |
| 합성 단체방 3명 | 1080 | +20 ~ +26 | ≤ −26 |
| 합성 1:1 (라벨 없음) | 1080 | — | ≤ +1 |
| 합성 1:1, 짧은 답장 다수 | 1080 | — | ≤ −1 |

신호는 폭의 1.9~2.9%, 잡음은 0.09% 다. `NAME_LABEL_INDENT_RATIO` 를 **0.01**
로 둔다. 신호까지 약 2배, 잡음까지 약 10배 여유가 있다.

폭 대비 비율로 두는 이유는 캡처 해상도를 우리가 정할 수 없기 때문이다.
720 과 1080 에서 픽셀값은 달랐지만 비율은 같은 자리에 모였다.

**이건 순위가 아니라 자격 요건이다.** 튀어나오지 않은 블록은 아무리 반복돼도
이름이 아니다.

한계. 프로필 사진을 숨기는 테마나, 이름을 말풍선과 같은 선에 맞추는 버전이
있다면 이름 라벨이 하나도 잡히지 않아 **단체방을 통째로 놓친다.** 실측한
캡처는 한 벌뿐이므로 이 위험은 남아 있다. 다만 실패 방향이 거부가 아니라
미탐이므로 7.2 의 판단과 같은 쪽이다.

### 7.5 왜 말풍선을 직접 보지 않는가

말풍선 안이냐 밖이냐가 진짜 기준이다. 7.4 의 들여쓰기는 그것을 **좌표만으로**
근사한 것이다. 그러면 말풍선을 직접 보면 되지 않느냐는 물음이 남는다.

두 가지를 실측했다. 둘 다 7.4 보다 나빴다.

**전역 기준선.** 화면 전체에서 왼쪽 블록 x 의 최빈값을 말풍선 기준선으로 삼고,
그보다 왼쪽인 것을 이름으로 본다.

| 캡처 | 기대 | 결과 |
| --- | --- | --- |
| 실제 1:1 | 이름 1개 | 1개 |
| 합성 단체방 3명 | 이름 3개 | **1개** |
| 합성 1:1 | 0개 | 0개 |

단체방에서 무너진다. **단체방은 이름 라벨이 많아서** 최빈값이 이름 자리로
잡힌다. 이름을 기준선으로 삼으니 이름이 보이지 않는다. 7.4 가 전역 기준선이
아니라 **자기가 이름표를 붙인 그 말풍선과 직접** 비교하는 이유다.

**픽셀 색.** 글자 왼쪽 6px 의 밝기를 재면 말풍선 색과 배경색이 갈린다.

| 종류 | 밝기 |
| --- | --- |
| 이름 라벨 (n=32) | 7 ~ 9 (배경) |
| 말풍선 본문 (n=78) | 중앙 40 (말풍선) |

갈리기는 한다. 그런데 **본문 78개 중 2개가 배경으로 읽혔다.** 말풍선 왼쪽
모서리에 붙은 글자는 6px 왼쪽이 이미 말풍선 밖이다. 같은 캡처에서 7.4 의
오분류는 0 이었다.

비용도 크다.

- `parse` 가 `OcrPage` 말고 이미지 바이트까지 받아야 한다
- 테마마다 색이 다르다. 다크는 검정 배경에 회색 말풍선, 라이트는 회색 배경에
  흰 말풍선과 노란 내 말풍선이다
- 2장은 OCR 엔진에게 **좌표**를 요구한다. 파서가 픽셀을 보기 시작하면 그 경계가
  흐려지고, 엔진을 바꿀 때마다 원본 이미지 취급 규칙이 따라붙는다

정확도가 더 낮고 비용이 크므로 채택하지 않는다. 다시 검토한다면 근거는
"픽셀이 더 정확하다"가 아니라 **"7.4 가 통하지 않는 테마를 만났다"** 여야 한다.

## 8. 텍스트 정규화

정규화의 목적은 두 가지다. 하나는 LLM 입력 토큰을 줄이는 것이고, 다른 하나는 의미 없는 변형을 제거해 분석 품질을 높이는 것이다.

| 규칙 | 변환 전 | 변환 후 |
| --- | --- | --- |
| 반복 문자 축약 (3회 초과 → 2회) | `ㅋㅋㅋㅋㅋㅋㅋ` | `ㅋㅋ` |
| 반복 기호 축약 | `!!!!!!` | `!!` |
| URL 치환 | `https://...` | `[링크]` |
| 사진 표기 | `사진`, `사진 3장` | `[사진]` |
| 이모티콘 표기 | `이모티콘` | `[이모티콘]` |
| 동영상 표기 | `동영상` | `[동영상]` |
| 파일 표기 | `파일: xxx.pdf` | `[파일]` |
| 연속 공백 | `안녕    하세요` | `안녕 하세요` |

정규화 후 빈 문자열이 되는 메시지는 제거하고 `droppedCount`를 증가시킨다.

반복 문자 축약은 감정 강도 정보를 일부 잃지만, `ㅋ`가 30번 반복되는 메시지 하나가 토큰 수십 개를 먹는 비용이 더 크다. 강도는 반복 여부(2회로 축약되었는지)로 남는다.

## 9. 이미지 간 중복 제거

스크롤 캡처는 인접 이미지의 경계가 겹친다. 이 구간을 제거하지 않으면 메시지 수가 부풀려져 모든 비율 지표가 왜곡된다.

```text
K = 10

for i in 0..n-2:
    tail = 이미지 i의 마지막 K개 메시지
    head = 이미지 i+1의 처음 K개 메시지

    (speaker, 정규화된 text) 쌍이 3개 이상 연속 일치하는
    가장 긴 구간을 찾는다

    발견되면 이미지 i+1에서 그 구간을 제거한다
```

3개 연속을 기준으로 삼은 이유는, 짧은 메시지(`ㅇㅇ`, `ㅋㅋ`)는 우연히 일치할 수 있어서 1~2개 일치로는 오탐이 나기 때문이다.

## 10. 샘플링

직렬화된 `ConversationData`의 예상 토큰이 설정된 상한을 넘으면 메시지를 추려낸다.

```text
상한 초과 시:
  앞부분 30개  (관계의 초기 맥락)
  뒷부분 50개  (현재 상태)
  중간 40개    (남은 구간에서 균등 간격 추출)
  = 총 120개

meta.sampled = true
```

뒷부분을 앞부분보다 많이 남기는 이유는, 관계의 **현재 상태**가 판단에 더 중요하기 때문이다. 손절 위험도와 답장 속도는 최근 데이터가 결정한다.

샘플링이 발생하면 `confidence`가 한 단계 강등된다(`관계-점수-계산-규칙.md` 11장).

**샘플링은 메시지를 잘라내는 것이지 LLM 호출을 나누는 것이 아니다.** 기준 명세의 LLM 1회 호출 원칙은 유지된다.

Parser 출력 직전에 검사한다.

## 12. 실패 처리 매핑

| 상황 | 오류 코드 |
| --- | --- |
| OCR 엔진 호출 실패·타임아웃 | `OCR_FAILED` |
| 인식된 텍스트 블록이 없음 | `NO_CONVERSATION_FOUND` |
| 좌우 판별된 블록이 전혀 없음 | `SPEAKER_DETECTION_FAILED` |
| 서로 다른 이름 라벨 2개 이상 | `GROUP_CHAT_DETECTED` |
| 정규화 후 메시지 15개 미만 | `TOO_FEW_MESSAGES` |
| 한쪽 화자만 존재 | `NO_CONVERSATION_FOUND` |

오류 메시지에 **대화 원문, 파일명, 좌표를 포함하지 않는다.**

## 13. 로깅 제약

기준 명세 5장에 따라 아래를 로그에 남기지 않는다.

- 대화 원문 텍스트 (정규화 전후 모두)
- OCR 블록의 `text` 필드
- 업로드 파일명

남길 수 있는 것은 블록 수, 메시지 수, 제거 건수, 처리 시간, 오류 코드 같은 **집계값과 식별자뿐이다.**

## 14. 검증 항목

OCR 엔진 후보를 평가할 때 아래를 실제 카카오톡 캡처로 측정한다.

| 항목 | 기준 |
| --- | --- |
| 화자 판별 정확도 | 좌우 판별이 틀린 메시지 비율 |
| 시각 인식률 | `timeSource`가 `unknown`이 아닌 비율 |
| 텍스트 정확도 | 한글 오인식률 |
| 처리 시간 | 이미지 1장당 소요 시간 |
| 건당 비용 | 이미지 1장당 과금액 |

기준 명세 8장에 따라 저비용 방식을 먼저 검증하되, **화자 판별 정확도가 기준에 못 미치면 비용이 낮아도 채택하지 않는다.** 이 지표가 틀리면 결과 전체가 틀린다.
