## 1. 문서 목적

이 문서는 서비스를 실제 사용자에게 공개하기 전에 갖춰야 할 **고지, 동의, 보안 조치**를 정의한다.

기술적으로 잘 만들어도 이 문서의 항목이 비어 있으면 공개할 수 없다. 이 서비스는 **동의하지 않은 제3자의 사적 대화**를 처리하기 때문이다.

## 2. 이 서비스의 특수한 위치

일반적인 웹 서비스와 결정적으로 다른 점이 하나 있다.

```text
일반 서비스:  사용자가 자기 데이터를 올린다
친구비 측정기: 사용자가 자기 데이터와 함께
              동의하지 않은 상대방의 데이터를 올린다
```

업로더는 자기 대화라고 생각하지만, 그 캡처의 절반은 **상대방이 쓴 글**이다. 상대방은 자기 메시지가 분석 서버로 전송된다는 사실을 모른다.

이 사실에서 아래 원칙이 나온다.

- **최소 수집**: 분석에 필요한 것 이상을 받지 않는다
- **최소 보관**: 필요한 시간 이상 두지 않는다
- **최소 노출**: 원문을 로그·응답·제3자 서비스로 흘리지 않는다
- **명확한 고지**: 업로더가 무엇을 하고 있는지 알게 한다

기준 명세 5장의 데이터 처리 원칙, `AI-모델-선정-보고서.md` 3장의 무료 티어 배제가 모두 여기서 나온 결론이다.

## 3. 서비스 이용약관에 담을 내용

정식 법률 검토를 받기 전의 초안이다. **변호사 검토 없이 그대로 게시하지 않는다.**

### 3.1 서비스의 성격

- 본 서비스는 **오락 목적**의 관계 분석 도구다.
- 결과는 통계적 추정이며, 실제 인간관계를 판단하거나 평가하는 근거가 아니다.
- 결과를 근거로 한 어떤 결정에도 서비스는 책임지지 않는다.

### 3.2 이용자의 의무

- **본인이 참여한 대화만 업로드한다.**
- 타인의 대화를 몰래 촬영하거나 전달받아 업로드하지 않는다.
- 업로드한 대화에 상대방의 민감정보가 담기지 않도록 스스로 확인한다.
- 결과를 상대방을 조롱하거나 괴롭히는 데 쓰지 않는다.

### 3.3 금지 행위

- 자동화 도구를 이용한 대량 요청
- 서비스의 분석 결과를 상업적으로 재판매하는 행위
- 타인을 사칭해 업로드하는 행위

### 3.4 연령

- **만 14세 미만은 이용할 수 없다.** 법정대리인 동의 절차를 두지 않기로 했기 때문이다.
- 이 제한을 첫 화면에서 고지한다.

## 4. 개인정보 처리방침에 담을 내용

### 4.1 수집 항목

### 4.2 수집하지 않는 것을 명시한다

무엇을 안 하는지도 함께 적는다. 사용자가 가장 걱정하는 부분이기 때문이다.

- 회원가입을 받지 않는다
- 분석 이력을 남기지 않는다
- 대화 원문을 로그에 남기지 않는다
- 대화 원문을 결과 응답에 담아 되돌려 보내지 않는다
- 업로드한 파일의 원래 이름을 저장하지 않는다

### 4.3 제3자 제공

분석 과정에서 아래 외부 서비스에 데이터가 전송된다. **이 목록은 실제 채택한 Provider에 맞춰 갱신해야 한다.**

#### 모델 제작사는 제3자가 아니다

채택 모델 `qwen/qwen3.8-27b` 는 Alibaba Qwen 팀이 만들었지만 **Apache 2.0 오픈 웨이트**다. Groq 이 공개된 가중치 파일을 받아 자사 하드웨어에서 실행한다.

**따라서 Alibaba 는 요청을 받지 않으며 제3자 제공 대상이 아니다.** 중국 회사가 만든 모델을 쓰는 것과 중국으로 데이터를 보내는 것은 다른 이야기다. 고지에 Alibaba 를 적으면 사실과 다르고, 반대로 이 구조를 설명하지 않으면 이용자가 오해한다.

`openai/gpt-oss-*` 도 같은 구조다. OpenAI 가 공개한 가중치를 Groq 이 돌리며 OpenAI 로 가지 않는다.

#### Groq 의 데이터 정책 근거

**개인정보처리방침이 아니다.** 그 문서는 API 고객 데이터를 명시적으로 제외하며, "GroqCloud 및 API 등 사업 제공물의 고객 데이터에는 이 정책이 적용되지 않는다"고 적고 있다. 근거는 아래 둘이다.

- Groq Services Agreement — `console.groq.com/docs/legal/services-agreement`
- Your Data in GroqCloud — `console.groq.com/docs/your-data`

| 항목 | 내용 |
| --- | --- |
| 학습·파인튜닝 이용 | 고객이 명시적으로 허락하지 않는 한 **금지** |
| 기본 보관 | 하지 않음 |
| 예외 | 장애 대응·악용 조사 시 **최대 30일** 임시 로그 |
| Zero Data Retention | 콘솔 Data Controls 에서 **직접 켤 수 있다.** 켜면 위 로그도 남지 않음 |

Groq 은 파운데이션 모델을 만들지 않는 추론 전용 사업자다. 학습 데이터 파이프라인 자체가 없어 구조적으로 유인이 없다.

**Global ZDR 을 켠다.** 콘솔 화면(2026-08-26 확인)에 이렇게 적혀 있다.

> Starting October 15, 2025, Groq may store inputs and outputs for up to 30 days, strictly for purposes of maintaining system reliability and compliance.

**기본값이 저장하는 쪽이다.** 켜지 않으면 대화 상대방의 사적 메시지가 30일간 Groq 에 남는다.

| 스위치 | 범위 | 우리 선택 |
| --- | --- | --- |
| **Global ZDR** | 조직 전체. 데이터 저장이 필요한 기능이 함께 비활성화된다 | **켠다** |
| Inference APIs ZDR | 추론 API 의 30일 저장만 해제 | Global 이 덮는다 |

Global 을 켜면 Batch API, 파인튜닝, 파일 저장이 막힌다. **우리는 `chat/completions` 하나만 쓰므로 잃는 것이 없다.** 파인튜닝은 애초에 대화를 모아둬야 가능하므로 우리 원칙과 양립하지 않는다.

무료 티어에서도 켜진다. 콘솔에서 확인했다.

Provider를 바꿀 때는 **이 표와 개인정보 처리방침을 함께 고친다.** 코드만 바꾸고 고지를 방치하면 사실과 다른 안내가 된다.

### 4.4 파기

- 정상 종료: 삭제 요청 즉시 파기
- 비정상 종료: TTL 5분 경과 시 자동 파기
- 조회되지 않은 작업: 주기적 정리로 파기

파기는 되돌릴 수 없다. 백업을 두지 않는다.

### 4.5 이용자의 권리

계정이 없고 식별자를 저장하지 않으므로 **열람·정정·삭제 요청 대상이 되는 개인정보가 남지 않는다.** 다만 이용자는 결과 화면에서 언제든 즉시 삭제를 요청할 수 있다.

### 6.2.1 전역 일일 상한

요청 제한이 **전부 IP 기준**이다. IP 하나가 하루 10건을 넘지 못하게 막지만, 서로 다른 IP 1,000개가 오면 하루 10,000건이 나간다. **전체를 막는 것이 없다.**

지금은 LLM 무료 티어라 한도를 넘으면 호출이 실패할 뿐 요금이 붙지 않는다. 그러나 유료로 전환하는 순간 이 구멍이 그대로 청구서가 된다. 개인이 무료로 여는 서비스에서 **예상 못 한 청구서는 서비스를 닫게 만드는 가장 흔한 이유다.**

그래서 IP와 무관한 하루 총량을 둔다.

```text
FC_SERVICE_DAILY_LIMIT 를 넘으면  →  SERVICE_DAILY_LIMIT (429)
```

`DAILY_LIMIT_EXCEEDED` 를 재사용하지 않는다. 그 코드의 문구는 "오늘 분석 가능한 횟수를 모두 사용했습니다"인데, 전역 상한에 걸린 사용자는 **자기 몫을 쓴 적이 없다.** 같은 코드를 쓰면 사실과 다른 말을 하게 된다.

기본값은 **400**이다. Groq 무료 티어의 하루 한도가 실측 500건이므로(요청 1,000/일 ÷ 건당 2회) 그보다 낮게 잡아 여유를 둔다. 한도에 닿기 전에 우리가 먼저 멈추는 편이 낫다. 외부 서비스가 끊어 주기를 기다리면 그 시점의 사용자는 원인을 알 수 없는 실패를 본다.

**이것으로 비용이 0이 되지는 않는다.** 서버비는 고정이고, 이 상한이 막는 것은 **LLM 호출량**뿐이다. 서버비까지 확실히 묶으려면 선불 요금제를 쓰고 결제 수단을 등록하지 않는다.

### 6.2.2 운영 종료일

이 서비스는 **기간을 정해두고 연다.** 종료일을 설정에 두고, 그날이 지나면 새 분석을 받지 않는다.

```text
FC_SERVICE_END_DATE 가 지나면  →  SERVICE_ENDED (410)
비워두면 무기한
```

**가장 위험한 것은 켜두고 잊는 것이다.** 관심이 식었는데 서버는 계속 도는 상태가 되면, 남의 대화를 계속 받으면서 아무도 보지 않는다. 그 사이 처리방침이 약속한 것들 — 신고 응답, 유출 시 72시간 통지, Provider 정책 변경 대응 — 이 지켜지지 않는다. **지킬 수 없는 약속을 계속 켜두는 것이 이 서비스에서 가장 큰 위험이다.**

날짜를 잊어도 서버가 먼저 멈춘다. 사람의 기억에 기대지 않는다.

**막는 것은 새 분석뿐이다.** 이미 진행 중인 작업의 상태 조회와 삭제는 계속 동작한다. 종료일에 걸린 사용자가 자기 결과를 잃지 않게 한다.

**서버 정지가 곧 과금 정지는 아니다.** VPS 요금은 인스턴스를 내려야 멈춘다. 종료일은 데이터를 더 받지 않기 위한 장치이고, 인스턴스 정리는 사람이 해야 한다. 점검표에 함께 적어둔다.

기준 시각은 한국 시간이다. UTC 로 두면 한국의 종료일 저녁이 이미 지난 날로 계산된다.

### 6.3 알려진 한계

정직하게 적어둔다. 감춰서 이득 볼 것이 없다.

- **전역 일일 상한은 프로세스 메모리에 있다.** 인스턴스를 재시작하면 0으로 돌아간다. 단일 인스턴스 전제에서는 문제가 없지만, 재시작이 잦으면 상한이 헐거워진다.
- **IP 기반 제한은 공용 네트워크에서 부정확하다.** 같은 와이파이의 여러 사용자가 한 IP로 묶인다. 반대로 IP를 바꾸면 제한을 우회할 수 있다. 계정이 없는 서비스의 구조적 한계다.
- **`jobId` 가 유출되면 결과를 볼 수 있다.** UUID v4라 추측은 사실상 불가능하지만, 링크를 공유하면 TTL 동안 누구나 열 수 있다.
- **`jobId` 는 배포 플랫폼의 접근 로그에 남는다.** URL 경로에 들어 있기 때문이다. 우리 애플리케이션 로그에는 남기지 않고 테스트로 막아두었지만, Cloud Run·프록시·CDN이 남기는 요청 로그는 우리가 통제하지 않는다. TTL이 5분이라 노출 창은 짧지만, **접근 로그를 볼 수 있는 사람은 그 시간 안에 결과를 조회할 수 있다.** 로그 열람 권한을 최소로 유지한다.
- **단일 인스턴스 전제다.** 작업 상태와 제한 카운터가 프로세스 메모리에 있다. 인스턴스를 늘리면 상태가 갈라진다.
- **동시 처리 수가 메모리에 묶여 있다.** 업로드 한 건이 최대 20MB이고 분석이 끝날 때까지 메모리에 남는다. 실측으로 동시 20건이 446MB였다. 512Mi 컨테이너에서는 동시성 8이 안전한 상한이다. 외부 오브젝트 스토리지로 갈아 끼우면 이 제약이 풀린다.
- **업로더가 상대방 동의를 받았는지 확인할 방법이 없다.** 고지와 약관으로 책임을 명확히 하는 것 외에 기술적 수단이 없다.

## 7. 사고 대응

| 상황 | 대응 |
| --- | --- |
| API 키 유출 | 즉시 폐기·재발급, 사용량 확인 |
| 비용 폭주 | 제한값을 낮추거나 서비스를 일시 중단. 예산 알림을 미리 걸어둔다 |
| 원문이 로그에 남은 것을 발견 | 해당 로그 즉시 파기, 원인 코드 수정, 재발 방지 테스트 추가 |
| 제공자가 데이터 정책을 변경 | 즉시 다른 Provider로 전환. 그래서 교체 가능한 구조로 만들었다 |
| 대량 악성 업로드 | 요청 제한 강화, 필요 시 업로드 차단 |
| 손을 뗄 때가 됨 | `FC_SERVICE_END_DATE` 로 새 분석을 막고, **VPS 인스턴스를 파기한다.** 서버 정지와 과금 정지는 다르다 |

**Provider 교체가 사고 대응 수단이라는 점이 중요하다.** 특정 업체에 코드가 묶여 있으면 정책이 바뀌었을 때 서비스를 멈추는 것 외에 선택지가 없다.
