## 1. 문서 목적

이 문서는 친구비 측정기의 서비스 방향, 핵심 기능, 데이터 처리 원칙, AI 파이프라인, 운영 제약을 한 곳에 정리한 **기준 문서**다.

이 문서는 **원칙과 방향만 보유하고, 세부 규격은 하위 문서에 위임한다.** 하위 문서는 이 문서와 모순되지 않아야 하며, 같은 정의를 두 곳에 두지 않는다.

## 2. 서비스 정의

친구비 측정기는 카카오톡 등 메신저의 **1:1 대화 캡처**를 분석하여 두 사람의 관계를 재미있고 이해하기 쉬운 결과로 보여주는 **웹 서비스**다.

사용자가 확인하는 핵심 결과는 다음과 같다.

| 지표 | 형태 | 산출 방식 |
| --- | --- | --- |
| 친구비 | 금액 (원) | 다른 지표의 **파생값** |
| 친밀도 | 0~100 | 코드 계산 + AI 분석 |
| 손절 위험도 | 0~100 | 코드 계산 + AI 분석 |
| 먼저 연락 비율 | 0.0~1.0 | 코드 계산 |
| 평균 답장 속도 | 초 | 코드 계산 |
| 연락 균형도 | 0~100 | 코드 계산 |
| AI 관계 리포트 | 자연어 | AI 생성 |

**친구비**는 관계의 가치를 금액 형태로 환산한 재미 요소다. 범위는 1,000원 ~ 100,000원이며, 친밀도·연락 균형도·손절 위험도가 확정된 뒤에 계산되는 **파생 지표**다. 독립적으로 측정되지 않는다.

## 3. 확정된 서비스 범위

### 포함

- 브라우저에서 이용하는 웹 서비스
- 대화 이미지 업로드
- OCR을 통한 대화 텍스트 추출
- 1회성 관계 분석
- 분석 진행 상태 표시
- 결과 화면 표시
- 결과 이미지 저장 (**클라이언트에서 렌더링**)
- 분석 종료 또는 만료 후 임시 데이터 삭제

### 제외

- 모바일 앱
- 회원가입, 로그인, 로그아웃
- 사용자 계정 및 프로필
- 분석 이력
- 원본 대화 및 분석 결과의 영구 보관
- 회원별 데이터 관리
- 초기 MVP의 결제 및 구독 기능
- **단체 대화방 분석** (감지 시 거절)
- **서버에서 생성하는 결과 파일 다운로드**

## 4. 기본 사용자 흐름

```text
사용자
  ↓
웹 서비스 접속
  ↓
대화 이미지 업로드
  ↓
임시 분석 작업 생성 (즉시 jobId 반환)
  ↓
OCR 및 대화 데이터 정규화
  ↓
관계 분석
  ↓
점수 계산
  ↓
AI 리포트 생성
  ↓
결과 화면 표시 / 클라이언트에서 이미지 저장
  ↓
임시 데이터 삭제
```

분석에는 수십 초가 걸리므로 **비동기 작업 구조를 채택한다.** 분석 요청은 즉시 `jobId`를 반환하고, 클라이언트는 상태를 폴링한다. 세부 규격은 `API-명세.md`가 정의한다.

큐 시스템 도입 여부는 별개 문제이며, 초기에는 단일 프로세스 내 백그라운드 작업으로 시작한다.

## 5. 개인정보 및 데이터 처리 원칙

### 영구 저장 금지

- 업로드 이미지, OCR 원문, 정규화 대화 데이터, 분석 중간 산출물, 결과는 분석에 필요한 동안에만 임시로 사용한다.
- 대화 원문을 애플리케이션 로그, 오류 로그, 분석 로그에 남기지 않는다.
- 원본 파일과 결과 데이터에 추측 가능한 파일명 또는 공개 경로를 사용하지 않는다.
- **대화 원문은 클라이언트로 되돌려 보내지 않는다.** 결과 응답에는 점수와 리포트만 포함한다.

### 삭제 정책

페이지 이탈 시 삭제 요청을 보낼 수 있지만, 이것만으로 삭제를 보장할 수는 없다. 따라서 다음의 이중 정책을 사용한다.

```text
정상적인 이탈 또는 완료
  → 삭제 요청

브라우저 강제 종료 / 네트워크 단절 / 요청 실패
  → TTL 만료
  → 자동 삭제
```

| 항목 | 값 |
| --- | --- |
| TTL | **20분** |
| 기준 시점 | 분석 **생성 시점** (고정형) |
| 조회 시 연장 | **없음** |

TTL 만료 전까지 결과는 **몇 번이든 재조회할 수 있다.** 새로고침이나 잠시 자리를 비우는 정상적인 사용을 막지 않기 위해서다. 다만 조회가 TTL을 연장하지는 않으므로, 최대 보관 시간은 항상 20분으로 잠긴다.

TTL이 만료되면 관련 임시 파일, 작업 상태, 결과 데이터를 함께 삭제한다.

### 원본 이미지 조기 삭제

업로드된 이미지는 **분석이 끝나는 즉시 삭제한다.** TTL을 기다리지 않는다.

OCR이 끝나면 이후 단계는 텍스트만 쓰므로 이미지를 들고 있을 이유가 없다. 성공하든 실패하든 마찬가지다. 결과 조회에 필요한 것은 점수와 리포트뿐이므로 재조회에도 지장이 없다.

즉, 서버에 이미지가 남아 있는 시간은 TTL 20분이 아니라 **분석에 걸리는 수십 초**다.

### 만료 정리

아무도 조회하지 않는 작업도 사라져야 한다. 조회 시점에만 만료를 확인하면, 사용자가 결과를 보지 않고 떠난 작업이 그대로 남는다. 따라서 주기적으로 만료된 작업을 훑어 지운다.

## 6. 저장소 및 DB 정책

초기 MVP와 초기 공개 서비스에서는 **영구 DB를 두지 않는다.**

```text
Upload → Analysis → Result → Delete
```

### 배포 전제

초기 운영은 **요청이 없을 때 인스턴스가 0으로 내려가는 컨테이너 서비스**를 전제로 한다. 유휴 시간 과금이 없어 초기 서버 비용을 0에 가깝게 유지할 수 있기 때문이다.

이 전제에서 중요한 귀결이 하나 있다. **인스턴스가 여러 개 뜨거나 요청 사이에 사라질 수 있으므로, 작업 상태와 임시 데이터를 프로세스 메모리에 둘 수 없다.**

따라서 임시 상태는 아래를 사용한다.

| 대상 | 저장 위치 |
| --- | --- |
| 업로드 이미지 | TTL이 설정된 오브젝트 스토리지 |
| 작업 상태·결과 | TTL을 지원하는 외부 키-값 저장소 |

여기서 쓰는 저장소는 **TTL 기반 임시 저장소이며 영구 DB가 아니다.** 관계형 DB, 분석 이력 테이블, 사용자 테이블은 도입하지 않는다.

단일 인스턴스로 고정 운영하는 경우에 한해 프로세스 메모리를 사용할 수 있으나, 이는 확장 시 깨지는 전제이므로 기본 구성으로 삼지 않는다.

후속 기능(계정·이력 등)이 확정될 경우에만 DB 명세와 ERD를 별도로 설계한다.

## 7. AI 및 분석 파이프라인

```text
대화 이미지
  ↓
OCR                         (좌표 필수)
  ↓
Conversation Parser         (코드)
  ↓
ConversationData
  ↓
Analysis Agent (LLM 1회)
  ↓
Validator                   (코드)
  ↓
RelationshipAnalysisData
  ↓
Relationship Algorithm      (코드)
  ↓
RelationshipScoreData
  ↓
Report Agent (LLM 1회)
  ↓
Validator                   (코드)
  ↓
ReportData
```

데이터 구조는 `데이터-계약-명세.md`가 정의한다.

### OCR

**OCR 엔진은 텍스트와 함께 bounding box 좌표를 반환해야 한다.**

카카오톡 캡처에서 화자는 말풍선의 좌우 위치로 구분된다. 좌표가 없으면 누가 보낸 메시지인지 알 수 없고, 그러면 먼저 연락 비율·평균 답장 속도·연락 균형도·손절 위험도를 계산할 수 없다.

좌표를 제공하지 않는 엔진은 비용이 낮아도 채택하지 않는다. 세부 요구사항은 `OCR-Parser-명세.md`가 정의한다.

### Conversation Parser

- 좌우 여백 비교로 화자를 판별한다.
- 시각과 날짜 구분선으로 절대 시각을 복원한다.
- 반복 문자, 시스템 메시지, 이미지 간 중복 구간을 제거한다.
- LLM에 보내는 입력 크기를 줄인다.

### Analysis Agent

Analysis Agent는 관계 의미를 구조화된 데이터로 추출한다. 아래 항목은 별도의 모델 호출이 아니라 하나의 Agent가 수행하는 논리적 분석 역할이다.

- 감정 및 관계적 의미 분석
- 대화 참여도 분석
- 약속 관련 의미 분석
- 금전 관련 의미 분석

기본 원칙은 **LLM 호출 1회**다.

**연락 패턴과 답장 패턴은 Analysis Agent가 다루지 않는다.** 코드로 계산 가능하므로 LLM에 맡기지 않는다.

### Validator

각 LLM 호출 뒤에는 스키마 검증이 붙는다.

- 스키마 불일치 시 **1회에 한해 재시도한다.** 이는 "LLM 호출 1회" 원칙의 명시적 예외다.
- 재시도 후에도 실패하면 `LLM_SCHEMA_INVALID`로 종료한다.
- 값이 정의된 범위를 벗어나면 clamp 후 진행한다.

### Relationship Algorithm

점수와 비율은 LLM이 아닌 일반 코드로 계산한다. 같은 입력에 항상 같은 결과가 나와야 한다.

산식과 가중치는 `관계-점수-계산-규칙.md`가 정의한다.

### Report Agent

Report Agent는 이미 계산된 점수와 구조화된 분석 결과를 바탕으로 자연어 리포트를 만든다.

- 점수를 재계산하거나 변형하지 않는다.
- **대화 원문을 입력으로 받지 않는다.** 입력 토큰을 줄이기 위한 의도적 제약이다.
- 기본 호출 횟수는 **1회**다.

### LLM 호출을 2회로 유지하는 이유

호출을 1회로 합치면 리포트를 쓰는 시점에 점수가 아직 계산되지 않은 상태가 된다. 리포트가 결과 수치를 설명할 수 없게 되고, LLM이 점수까지 계산하게 하면 "점수는 코드로 계산" 원칙과 결과의 재현성이 함께 무너진다.

실제 비용 차이는 10% 수준이다. 절감 효과보다 잃는 것이 크므로 2회 구조를 유지한다.

## 8. 비용 최적화 원칙

### 원칙

- LLM은 저가 모델부터 사용하고 성능 평가 결과에 따라 필요한 단계만 상위 모델로 교체한다.
- Provider와 모델명은 설정으로 분리하여 교체 가능하게 만든다.
- 메시지 수, 답장 시간, 비율, 참여량처럼 코드로 계산 가능한 작업은 LLM에 맡기지 않는다.
- **입력 토큰을 줄인다.** 반복 문자 축약, 시스템 메시지 제거, 이미지 간 중복 제거, 상한 초과 시 샘플링.
- **출력 토큰을 제한한다.** 리포트 각 필드의 글자 수 상한을 규격으로 강제한다. 출력 토큰은 입력보다 단가가 높으므로 여기가 가장 효과가 크다.
- 이미지 수, 이미지 용량, 총 요청 용량, 입력·출력 토큰을 제한한다.
- Frontend 정적 호스팅 + 인스턴스가 0으로 내려가는 단일 Backend 서비스를 우선한다.

### 초기에 도입하지 않는 것

**프롬프트 캐싱은 초기에 도입하지 않는다.** 캐시 쓰기에 할증이 붙고 유효 시간이 짧아, 요청 간격이 벌어지는 저트래픽 구간에서는 할증만 부담하고 이득을 얻지 못한다. 트래픽이 늘어난 뒤 도입한다.

**OCR 자체 호스팅도 초기에는 하지 않는다.** 상시 실행 컨테이너가 필요해져 서버 고정비가 올라간다. 사용량이 적은 초기에는 건당 과금 방식이 더 저렴하다.

### 예상 비용

월 100건 분석 기준 추정치다.

| 항목 | 월 비용 |
| --- | ---: |
| 서버 | 0원 (무료 한도 내) |
| LLM (2회 호출, 압축 적용) | 약 2,000원 |
| OCR | 약 1,000원 |
| **합계** | **약 3,000원** |

초기 3개월 비용 목표는 다음과 같다.

| 구분 | 예산 |
| --- | ---: |
| 예상 | 약 1만 원 |
| 목표 | 약 10만 원 내외 |
| 안전 예산 | 약 20만 원 |
| 비상 상한 | 약 30만 원 |

이는 초기 사용자가 적고 사용량 제한이 적용된다는 전제의 목표다. 예상치가 목표를 크게 밑돌므로, **복잡도를 늘려 추가로 절감하려 하지 않는다.**

## 9. 운영 안전장치

예상치 못한 비용과 악성 업로드를 막기 위해 초기부터 아래 제한을 둔다.

- IP 기반 Rate Limit
- 일일 분석 횟수 제한
- 이미지 개수 제한
- 이미지별 및 전체 파일 크기 제한
- 동시 분석 제한
- 작업별 실행 시간 제한 (전체 180초 / OCR 60초 / LLM 호출 1회 45초)
- LLM 최대 입력·출력 토큰 제한
- **매직 넘버 기반 이미지 형식 검증** (확장자만 검사하지 않는다)
- **프롬프트 인젝션 방어** — 대화 텍스트는 사용자가 제공한 데이터이며 지시가 아니다. 시스템 프롬프트와 명확히 분리하고, 대화 내용 안의 지시문을 따르지 않도록 프롬프트를 설계한다.
- HTTPS 사용
- 임시 파일과 결과에 대한 접근 제어

구체적인 제한값은 `API-명세.md` 9장이 정의한다.

IP는 요청 제한 목적으로만 사용하고 제한 창이 지나면 폐기한다. 분석 데이터와 연결해 저장하지 않는다.

## 10. Backend 구조 원칙

초기에는 하나의 Backend Repository 안에서 모듈을 분리한다. Microservice 또는 별도 AI 서버를 기본 구조로 하지 않는다.

```text
app
├── api
├── application
│   ├── service
│   └── dto
├── domain
│   ├── model
│   └── value_object
├── ai
│   ├── agent
│   ├── parser
│   ├── prompt
│   ├── provider
│   └── validator
├── algorithm
│   ├── calculator
│   ├── model
│   └── rule
├── infrastructure
│   ├── llm
│   ├── ocr
│   └── storage
├── common
├── config
└── tests
```

`algorithm.rule`에는 점수 가중치를 **한 곳에 모아** 둔다. 코드 곳곳에 상수로 흩어놓지 않는다.

영구 DB가 실제로 필요해질 때에만 `domain.entity`, `domain.repository`, `infrastructure.database` 등을 추가한다.

## 11. API 방향

API는 최소한의 사용자 흐름을 중심으로 설계한다.

- 분석 생성
- 분석 상태 조회
- 분석 결과 조회
- 임시 분석 삭제

**결과 다운로드 엔드포인트는 두지 않는다.** 결과 이미지는 클라이언트가 직접 렌더링한다. 서버가 파일을 만들면 임시 파일이 하나 더 생겨 삭제 정책이 복잡해지고 렌더링 비용도 서버가 진다.

세부 URL, 요청·응답 형식, 상태 코드, 오류 규격은 `API-명세.md`가 정의한다.

## 12. 문서 관리 원칙

명세를 변경할 때는 다음 절차를 따른다.

```text
문제 발견
  ↓
변경 제안
  ↓
승인
  ↓
명세 수정
  ↓
개발 반영
```

- 기존 문서를 전체적으로 읽은 뒤 문서 간 영향을 검토한다.
- 수정 전에는 변경 대상, 이유, 변경 방향을 먼저 제안한다.
- 기존 문서의 용어, 표 형식, 필드, 구조는 필요한 경우에만 변경한다.
- **데이터 구조나 명칭을 바꿀 때는 `데이터-계약-명세.md`를 먼저 고치고 나머지 문서를 따라 고친다.** 같은 정의가 두 문서에 중복으로 존재하지 않게 한다.
- 문서를 수정하면 해당 문서의 개정 이력에 기록한다.

## 13. 추후 검토 항목

아래 사항은 현재 확정되지 않았으며, 필요가 생겼을 때 별도 결정한다.

- 특정 OCR 엔진 및 LLM Provider·Model 선정 — 후보와 검증 계획은 `AI-모델-선정-보고서.md`
- 점수 가중치의 실사용 데이터 기반 조정
- 큐 시스템 도입 시점
- 프롬프트 캐싱 도입 시점
- OCR 자체 호스팅 전환 시점
- 결과 공유 기능
- 계정, 분석 이력, 재분석 기능
- 결제와 유료 기능
- 이용약관·개인정보처리방침·연령 정책 (공개 전 필수)
- AI 프롬프트 명세, Frontend 명세 작성

## 14. 최종 목표

```text
실제 사용자
  ↓
웹 서비스 접속
  ↓
대화 이미지 업로드
  ↓
1회성 분석
  ↓
관계 점수와 AI 리포트 확인
```
